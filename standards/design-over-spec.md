# design over 专项标准

## 1. 目的

为仓库内所有 AI 助手提供统一的 `design over` 打标判断口径。

这里的 `design over` 指的是：**当前页面范围内的需求设计与 UI 设计已达到可交付、可对照、可继续联调的完成态**，可以在迭代索引或对应入口上标记 `design over`。

它**不是**：

- 代码开发完成
- 接口联调完成
- 所有上下游页面全部完结
- 同组页面可以顺手一起打标

---

## 2. 适用场景

当用户提出以下任一请求时，必须读取本文件：

- “这个页面能不能打 `design over`”
- “帮我检查是否可打标”
- “按 design over 标准验一下”
- “这个页面是否可以收口”
- “给不同大模型统一一套打标规则”

---

## 3. 结论枚举

检查结论只允许输出三种：

1. `可打标`
2. `不可打标`
3. `待确认`

说明：

- `可打标`：已满足本文件的通过条件，且无阻塞项。
- `不可打标`：存在明确阻塞项，当前不能打标。
- `待确认`：页面本身接近完成，但仍缺少用户确认、范围确认或关键依赖确认。

---

## 4. design over 的最小成立条件

一个页面要满足 `design over`，至少同时满足以下 5 类条件：

### 4.1 范围收口完成

- 本次需求范围已落到目标页面或目标链路中
- 用户本轮明确点名的问题已修完，或已被用户明确排除在本轮范围外
- 没有遗漏本轮必需的状态、字段、入口、反馈或结果页承接

### 4.2 页面原型完成度达标

- 页面主体结构完整，真实用户看到的内容已稳定
- 页面中不存在明显占位、错位、未定稿文案、临时拼接块
- 页面内没有混入开发说明、测试提示、版本摘要、模拟操作说明
- 页面内没有暴露技术实现细节（如接口名称、后端服务名、微服务标识、第三方系统代号），用户可见文案应使用业务语言而非技术语言
- 页面不存在辅助文本或副标题泛滥，不得用大量说明性文字填充界面；每个区块最多一条辅助说明，能省则省
- 页面不存在冗余指示文案（如用户已选择微信支付后仍提示"点击跳转微信支付"）；控件状态本身已能传达的信息，不得再用文字重复说明

### 4.3 模拟操作面板完成度达标

- 移动端模拟操作统一放在手机模型右侧独立区域（参考标杆：扫码盘点 `.desktop-panel`）
- 面板只承接演示控制，不污染手机页面正文；手机页面内不得出现任何仅供演示/调试的按钮、文字或状态标记
- 面板结构遵循固定层级（自上而下）：需求文档按钮 → 标题 → 一句话说明 → 演示步骤（2~4 条，编号式）→ 页面路径信息 → 控制按钮区 → 可选指标区；不得随意增删层级或调换顺序
- 面板路径信息必须标注当前页面名和上级页面名，与页面真实导航层级一致
- 控制按钮只负责触发手机页面内的状态变更（如模拟扫码、切换状态），不得在面板内放置跳转到其他页面的链接

### 4.4 抽屉完成度达标

- 需求文档抽屉与 CSS 规范抽屉均可用
- 抽屉结构、排版、关闭按钮、Tab、宽度符合成熟样式基线
- 抽屉正文与页面实际内容一致，不存在“页面已改、抽屉未改”或相反情况

### 4.5 无明显误导

- 不存在误导性假交互、假状态、假文案
- 若某按钮为静态承接位，抽屉中必须明确沿用既有逻辑，不能写成新能力
- 不存在明显实现残渣，如字符串拼接片段、错乱标签、样式污染

---

## 5. 直接阻塞打标的情况

出现以下任一情况，结论必须是 `不可打标`：

1. 用户刚指出的问题尚未修正
2. 页面与需求抽屉口径不一致
3. 抽屉缺失、打不开，或只有需求文档没有 CSS 规范
4. 页面中混入开发备注、测试提示、模拟操作说明等非真实用户内容
5. 主流程未闭环，关键结果态/异常态缺失且属于本轮范围
6. 右侧面板混入手机正文，或手机正文承担了演示控制职责
7. 仍存在明显假交互、误导性占位、临时文案
8. 残留明显模板/拼接问题，如 `'+`、`</table>`、`'<tr` 等泄漏到正文
9. 当前页面并非用户点名页面，也不是本轮明确收口页面，却试图顺手打标
10. 需求抽屉中，任一功能区的全部规则与另一已完成页面的对应功能区逐条相同，且该页抽屉已声明"复用XX页""与XX一致""沿用既有逻辑"，但仍将被引用页的规则原文整体搬入本页抽屉
11. 未重新执行本文件的检查，仅继承接力文档、上一位 AI、审阅报告或历史结论中的"可打标"判断
12. 涉及导入、下载模板、业务弹窗说明、页面正文、需求抽屉、CSS 规范、独立 `js/docs.js` 或 `需求文档.md` 时，未完成口径一致性矩阵，或矩阵中任一来源存在冲突
13. 用户已明确确认的字段、默认值、必填/选填、失败归类、空值规则、后续链路或待确认项，仍在页面、模板、弹窗或抽屉中保留旧口径

---

## 6. `待确认` 的适用情况

出现以下情况时，优先给 `待确认`，而不是直接 `可打标`：

- 页面本身已基本完成，但用户尚未确认本轮收口
- 页面是否纳入本次打标范围仍不明确
- 结果页 / 关联页是否必须一起检查仍存在歧义
- 视觉和文档都基本齐，但仍有一项关键业务口径待产品确认

---

## 7. 检查维度

检查 `design over` 时，统一按下面 6 个维度逐项判断。

### 7.1 页面结构

- 页面类型判断正确
- 真实页面正文只保留用户可见内容
- 头部、返回、底部操作、主要卡片层级清晰
- 视觉样式稳定，无明显未收口区域

### 7.2 主流程与状态

- 主流程闭环完整
- 本轮范围内的默认态、成功态、失败态、空态、限制态表达完整
- 页面状态与按钮反馈逻辑一致

### 7.3 模拟操作面板

- 位于手机模型右侧独立控制区
- 顶部有统一风格的 `需求文档` 按钮
- 有标题、说明、操作步骤、页面路径、控制按钮
- 只提供演示承接，不往页面正文塞“开发操作”

### 7.4 需求文档抽屉

#### 7.4.1 组织方式

- 抽屉按**功能分区闭环**组织，每个功能区自包含字段定义、交互规则和边界说明，读者不需要跨分节拼图
- 不得按抽象维度拆出独立的"交互规则"或"异常与边界"分节；这些内容必须内联到对应功能区中
- 每个功能区内的规则用 key-value 卡片呈现（如 显隐/触发/行为/边界），确保一条规则只出现一次

#### 7.4.2 各分节职责与边界

- **筛选规则**：只写控件类型、输入/选择规则、默认值、数据来源
- **字段说明**：只写字段的展示规则（枚举值、为空展示、高亮条件）；操作列按钮的显隐规则不在此处写，归功能区
- **字段与接口关联**：只写**页面展示字段**与后端接口/数据源的对应关系；判断标准——该行的第一列必须是页面上真实展示的字段名（如"卡号""到期时间""站点名称"），不能是动作名、按钮名、操作结果名或流程节点名。以下内容**禁止**出现在字段与接口关联中：
  - 按钮动作及其接口来源（如"确认绑定 → 本地绑定关系写入"）——归功能区，用 `{ key: '接口', value: '...' }` 闭环
  - 动作执行结果的回写链路（如"绑定结果回写 → 本地绑定台账/列表缓存"）——归功能区"行为"规则
  - 导入/提交等操作的处理结果（如"导入结果 → 本地导入处理结果"）——归功能区"结果"或"行为"规则
  - 流程节点间的数据传递（如"提交返回编号 → 用户续费提交.data"）——如果是页面展示字段则保留，如果是内部传递逻辑则归功能区
- **功能区**（按钮/操作区）：自闭环显隐条件 + 交互行为 + 边界限制 + 接口来源；这是唯一写按钮完整逻辑的地方；按钮的接口来源用 `{ key: '接口', value: '...' }` 闭环，不依赖 relationRows 补充
- **状态与分支**：仅用于存在跨按钮状态流转的页面（如订单状态机：待支付→已支付→已发货→已完成）；列表页、详情页、表单页不存在跨按钮状态流转，不使用此分节
- **导入/表单字段**：必填/选填、格式限制、字段为空失败、失败明细归类、重复校验和后续链路归导入或表单功能区，不归列表字段

#### 7.4.3 禁止出现的重复

- 同一条规则不得出现在两个分节中（如续费按钮显隐不得同时在字段说明和功能区各写一遍）
- 字段枚举定义（如绑定状态=已绑定/待绑定/绑定异常）归字段说明；该枚举对按钮的影响（如待绑定不展示续费）归功能区
- 统计卡口径随筛选联动的规则，写在查询功能区，不在字段说明中重复
- 列表字段只写展示规则，不得混入必填/选填、字段格式、导入失败、重复校验、后续链路或计费规则
- 筛选规则不得为每个筛选字段重复写“按该字段查询”“非空时查询”等无信息量说明；查询方式沿用既有逻辑时，不另起精确/模糊/接口确认口径
- 按钮的接口来源只写一次：要么在功能区的 `{ key: '接口' }` 中，要么在字段与接口关联中，不能两处都写；默认优先在功能区闭环
- 动作结果（如"绑定结果回写""新增结果回写""导入结果"）不是页面展示字段，禁止出现在字段与接口关联中，必须在功能区"行为"或"结果"规则中闭环

#### 7.4.4 写作口径

- 抽屉默认直入业务规则，不铺垫页面定位、角色介绍、测试套话
- 陈述句优先，先结论后说明；禁止"大概/差不多/看情况/先这样/应该是"
- 对"沿用既有逻辑"场景，明确写沿用，不自行扩写成新功能
- 新增逻辑优先内联标注到具体条目，不写顶部泛化摘要代替正文定位
- 未确认的业务推断必须放进待确认项，不得写成既定规则

#### 7.4.5 标杆页的复用边界

- 标杆页（如扫码盘点、门牌号投递）的**排版基线、阅读体验、卡片样式**是参考标准，新页面必须对齐
- 标杆页的**分节结构**不是强制模板：标杆页使用的是旧版结构（包含页面定位/角色与入口/交互规则/异常与边界/测试注意事项/验收标准等分节），新页面按本文件 7.4.1-7.4.3 的规则组织，不因标杆页有这些分节就跟着写
- 具体差异：新页面不写"页面定位""角色与入口""测试注意事项""验收标准"；不拆独立的"交互规则""异常与边界"分节；改为功能区闭环组织
- 新页面与标杆页对齐的是：抽屉宽度、字号、行高、分节标题样式、卡片圆角、表格排版、关闭按钮样式

#### 7.4.6 跨页功能复用时的抽屉内容

当本页的某个功能区与另一已完成页面的对应功能区完全一致时，禁止在被引用页和本页各维护一份相同内容：

- 禁止将被引用页的规则原文、字段定义、交互说明逐条搬入本页抽屉——与本页当前需求描述无差异的内容，不写第二遍
- 该功能区只写一句引用声明，格式为"复用{页面名}的{分区名}说明"，并确保接收方能根据声明定位到被引用页的对应分节
- 仅在本页抽屉中保留与引用页存在差异的内容；如果整个功能区无差异，则该功能区整体用一句引用替代
- 禁止出现"进入本页前由运营人员在站点列表勾选""勾选后展示禁止取件原因文本域"等在引用页已完整描述且本页无差异的规则语句

判断标准：如果删除本页该功能区的全部内容后，对该分区的理解完全依赖引用页即可还原——则本页只应保留引用声明，不应保留原文。

#### 7.4.7 单页内部的重复禁止

以下属于 7.4.3 的延伸，同样造成信息冗余：

- 禁止在"页面内容"中列举已在"字段规则""交互规则"等分节中逐条说明的字段和能力清单
- 页面内容只写路径、入口来源、底部按钮等无法归入其他功能区的顶层信息
- 禁止使用"表单包含导入按钮、运单号、快递公司..."把页面所有控件罗列一遍——这些控件的规则已在各自功能区闭环

### 7.5 CSS 规范抽屉

- 与需求文档共用排版基线
- 不是纯文本堆砌
- 能稳定展示色块、字号、间距、圆角等可视化信息

### 7.6 文案与边界真实性

- 文案是当前页面真实会出现的口径
- 不虚构不会发生的异常
- 对“沿用既有逻辑”场景，明确写沿用，不自行扩写成新功能
- 接力文档、历史审阅结论、上一位 AI 的结论只能作为输入线索，不得作为 `可打标` 依据直接继承
- 用户本轮明确纠偏的内容优先级高于接力文档、历史页面、旧模板和旧抽屉正文；完成后必须确认旧口径已清除

### 7.7 口径一致性矩阵

`design over` 检查必须先判断目标页是否需要口径一致性矩阵。出现以下任一对象时，必须执行矩阵；否则不得输出 `可打标`：

- 页面真实正文、筛选区、列表字段、详情字段或状态标签
- 业务弹窗、业务抽屉、导入说明、操作确认文案
- 需求文档抽屉、CSS 规范 Tab、独立 `js/docs.js`、`需求文档.md`
- 下载模板、xlsx / csv 表头、示例数据、字段顺序
- 接力文档、开发执行文档、接口文档、用户本轮纠偏项

矩阵至少逐项核对：

| 核对项 | 必查口径 |
| --- | --- |
| 字段 | 名称、顺序、是否展示、是否进入模板、是否进入列表/详情 |
| 必填/选填 | 页面提示、模板星号、抽屉字段表、失败原因是否一致 |
| 默认值 | 空值、默认选项、默认状态、默认品牌或默认金额是否一致 |
| 失败归类 | 哪些情况进入失败明细、哪些情况生成订单、哪些情况为空 |
| 后续链路 | 是否进入收款、下单、面单、账单、对账或其他端展示 |
| 待确认项 | 用户已确认的内容不得继续保留为待确认；未确认内容不得写成事实 |
| 旧口径残留 | 旧默认值、旧必填星号、旧失败处理、旧待确认项、旧说明必须检索清除 |
| 虚构规则 | 页面、模板或抽屉中不得出现不存在的默认值、默认计费、默认金额、默认品牌或反向否定说明 |

输出 `可打标` 前必须明确说明矩阵结论：

- `已完成矩阵，全部一致`
- `不适用矩阵`，并说明为什么目标页不存在上述对象
- 任一来源冲突时只能输出 `不可打标`，并列出冲突来源和修复对象

## 8. 移动端标杆页

移动端 `design over` 判断，默认以下页面为**标杆来源**。

这些标杆用于统一：

- 页面与手机模型的组织方式
- 右侧模拟操作面板的布局与职责边界
- 需求文档抽屉的布局、字号、分节和阅读体验
- `需求文档` 按钮、路径信息、控制区的成熟样式

### 8.1 标杆 A：扫码盘点

- 页面：`field-app/main/pages/扫码盘点.html`
- 抽屉文档：`field-app/main/js/docs.js` 中 `inventory-warning`
- 抽屉实现：`field-app/main/js/doc-panel.js`

适合作为标杆的点：

- 深色背景 + 中置手机模型 + 右侧深色帮助卡
- `需求文档` 按钮置于右侧面板顶部
- 面板内含标题、说明、步骤、页面路径、控制按钮、关键指标
- 抽屉排版成熟，分节清晰，文档维度完整

### 8.2 标杆 B：门牌号投递

- 页面：`field-app/station-ops/pages/编号投递.html`
- 抽屉文档：`field-app/station-ops/js/docs.js` 中 `doorplate-delivery`
- 抽屉实现：`field-app/station-ops/js/doc-panel.js`

适合作为标杆的点：

- 页面、右侧模拟操作面板、抽屉三者边界清晰
- 面板内说明、路径、控制按钮组织稳定
- 抽屉文档已覆盖页面定位、搜索、展示区域、排序、交互、异常、测试、验收等完整结构
- 适合作为移动端列表/选择型页面的标杆

### 8.3 标杆使用方式

标杆是**抽象基线**，不是逐像素复刻要求。

允许变化：

- 业务配色
- 页面内容模块
- 分节标题命名
- 控制按钮数量
- 具体文案与业务规则

不允许偏离的，是以下抽象层：

- 手机页面与右侧控制区分层关系
- 面板职责边界
- 抽屉阅读体验与排版基线
- 文档覆盖维度
- 用户页面与设计辅助内容的隔离方式

## 9. 页面、面板、抽屉的统一标准

### 9.1 页面标准

- 主页面必须能表达本轮真实需求
- 关键交互入口与结果承接明确
- 不得把“给开发/给评审看的说明”塞进真实页面

### 9.2 模拟操作面板标准

移动端默认参考以下结构：

1. `需求文档` 按钮
2. 面板标题
3. 一句页面说明
4. 2~4 条演示步骤
5. 页面路径信息（当前页 / 上级页）
6. 控制按钮区
7. 可选的静态说明块 / 指标块

允许按场景删减，但不能把这些内容挪进手机页面正文。

### 9.3 抽屉标准

- App / 小程序默认宽度 `780px`
- 默认打开，可手动关闭
- 无遮罩，不阻断页面交互
- `需求文档` 与 `CSS规范` 两个 Tab 必须共存
- 关闭按钮、Tab、排版、分节标题统一复用成熟实现

## 10. 检查输出格式

以后任何模型在被要求“检查是否可打 design over”时，统一按下面格式输出：

### 10.1 必须输出的字段

1. `结论`：可打标 / 不可打标 / 待确认
2. `检查对象`：本次检查的页面路径
3. `对照标杆`：使用了哪个标杆页
4. `是否继承历史结论`：必须写明是否重新检查；不得只继承接力或历史结论
5. `口径一致性矩阵`：已完成 / 不适用 / 未完成；若完成，列出核对过的来源
6. `通过项`：已满足的关键条件
7. `阻塞项`：阻止打标的问题；若没有，写“无”
8. `建议动作`：下一步该补什么，或说明可直接打标

### 10.2 推荐输出示例

```md
结论：不可打标

检查对象：
- field-app/station-ops/pages/某页面.html

对照标杆：
- 页面与右侧面板：门牌号投递
- 抽屉排版：扫码盘点 / 门牌号投递共用抽屉基线

是否继承历史结论：
- 否，已按本文件重新检查

口径一致性矩阵：
- 已核对页面正文、业务弹窗、需求抽屉、下载模板、接力口径
- 发现页面中的按钮文案与抽屉规则不一致

通过项：
- 页面主体结构已完整
- 右侧面板已独立，不污染手机正文
- 需求文档抽屉已接入

阻塞项：
- CSS 规范抽屉缺失
- 页面中的按钮文案与抽屉规则不一致
- 用户刚指出的空态问题尚未修正

建议动作：
- 先补 CSS 规范抽屉
- 对齐页面与抽屉口径
- 修完用户指出问题后再复检
```

## 11. 打标权限边界

- `design over` 只能用于用户明确点名页面，或当前任务明确收口页面
- 不得顺手给同组其他页面补标
- 若页面仍在持续改动、口径未冻结，不建议提前打标

## 12. AI 执行约束

用户指出抽屉内容存在"太挤""阅读体验差""看不懂""混乱"等不满，但未给出具体修改方案时，AI 必须：

- 停止执行，不得直接改文件
- 输出修改提案，标明修改前后的差异
- 等待用户确认后才执行
- 禁止自行猜解用户意图后直接写入

用户已给出明确方案的（如"拆成独立卡片""改为一行一条"），不在此约束范围内。
