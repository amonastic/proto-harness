# 实施决策记录

只记录会影响实现路径、可逆性或交付口径的选择；普通实现细节不在此重复。

## D1 渲染层采用原生 ES Modules，而非 React/TypeScript 构建链

- 决策：Electron 渲染层使用原生 HTML/CSS/ES Modules；业务内核为 Node ESM + JSDoc。
- 理由：方案将 React/TS 列为推荐默认，但本任务要求最小充分实现并交付可安装产物。原生方案不引入 Vite/TS 编译链，安装与打包路径更短，仍可被 Playwright 与 node:test 验证。
- 影响：组件复用依靠模块导出，不依赖框架；若后续需要 React，可替换渲染层而不改内核。
- 可逆性：可逆。

## D2 首版生产运行时选择 OpenAI 兼容 HTTP 适配器

- 决策：实现统一运行时接口，生产适配器为 OpenAI 兼容 `/chat/completions`；不接入 OpenCode。
- 理由：本机未安装 OpenCode，无法验证其版本、权限边界与恢复行为；方案明确允许在必要条件无法满足时切换适配器，且不改变项目数据格式。
- 影响：支持 DeepSeek、OpenAI 兼容网关、Ollama/LM Studio 等；Model 配置保留 baseUrl/model/key。
- 可逆性：可逆；后续实现 OpenCode 适配器即可替换。

## D3 无模型配置时使用本地启发式分析器，并显式标注

- 决策：默认 `local-heuristic`，界面、产物 `source` 字段与交付清单均标注「本地规则分析」；不使用 dry-run 冒充模型。
- 理由：真实模型凭据缺失不构成工程阻塞；完整旅程需要可重复验证。启发式分析只从用户输入与来源材料提取，不生成行业参数。
- 影响：未配置模型时仍可完成完整旅程；分析质量与模型模式不同，文档明确说明。
- 可逆性：可逆。

## D4 文件型项目存储与原子写入

- 决策：实体按 JSON 文件存储；规则修订分文件；写入使用临时文件 + rename；`.runtime` 可重建。
- 理由：符合方案「可读文件为权威记录」；便于 Git、双机与人工审查。
- 影响：索引是派生数据；跨文件变更通过提案与指针更新分步提交。
- 可逆性：可逆。

## D5 打包使用本地 Electron dist + @electron/packager + hdiutil

- 决策：不使用 electron-builder 的远程 Electron 下载；从 `node_modules/electron/dist` 打包，ad-hoc 签名，`hdiutil` 生成 DMG。
- 理由：GitHub 直连受限；本机无 Developer ID。该路径可在无远程二进制下载的情况下生成可安装产物。
- 影响：产物未签名、未公证，首次打开需右键打开或移除隔离属性；不得称为正式发行包。
- 可逆性：可逆；后续有证书时可替换签名步骤。

## D6 pen.dev 只做能力探测与绑定记录

- 决策：不实现真实 MCP 设计操作；设置/交付中显示「未检测到 pen.dev」，任务保留并说明降级。
- 理由：本机无 pen，无法验证文档定位、节点引用与导出；方案要求不将降级结果伪装成已生成设计文件。
- 影响：HTML 主链完整；pen 相关步骤标为未完成。
- 可逆性：可逆。

## D7 验证采用 node:test + Playwright Electron

- 决策：内核与适配器用 node:test；UI 旅程用 `playwright-core` 的 `_electron` 驱动真实 Electron。
- 理由：验证安装前的真实交互与持久化，而不是只测纯函数。
- 影响：E2E 依赖本机图形环境；截图与项目文件共同作为证据。
- 可逆性：可逆。

## D8 应用落位 `apps/desktop`，不修改现有仓库规则与页面

- 决策：新增独立子系统；根 `package.json`、`AGENTS.md`、`harness/`、`standards/`、现有页面均不改。
- 理由：保护既有资产与规则；应用是可独立打包的产品，不是设计稿页面。
- 影响：根仓库的机检命令不覆盖应用；应用有独立测试与打包脚本。
- 可逆性：可逆。

## D9 规格生成按需求语义选择页面类型，并支持多页

- 决策：本地规格生成器按需求文本与分析结果推断 `form` / `list` / `board` / `settings` / `dashboard` / `detail`，在提交与管理并存时生成多页；模型返回的 `pages` 全部进入原型渲染，不再只取第一页。
- 理由：独立探针复现了报名、工单、打印设置都落到同一表格页；固定单页模板不满足需求到设计的对应关系。
- 影响：需求类型不同会得到不同的字段、控件、状态与页面结构；模型规格失败时显式回退本地并记录警告。
- 可逆性：可逆。

## D10 裁决后生成 resolved 分析，保留现行规则时按现行规则出产物

- 决策：裁决应用后写 `analysis-resolved.json`，生成链读取该文件而不是原始分析。保留现行规则时使用中性标题「按现行规则处理」，把被否决口径列入 `rejected_changes`，产物不得实现新口径。
- 理由：原实现把原始分析中的新规则继续喂给生成，导致用户选择保留后页面仍要求实施被否决规则。
- 影响：需求文档保留原始输入与裁决记录；原型和交付按裁决后的口径生成。
- 可逆性：可逆；原始分析仍保留。

## D11 交付创建时冻结产物副本

- 决策：创建交付时把产物复制到 `deliveries/<id>/frozen/`，manifest 记录冻结路径与哈希；导出只读取冻结副本并校验哈希。
- 理由：原导出读取活产物，交付后修改原型再重新导出会改写历史交付，违背固定版本要求。
- 影响：历史交付可复现；活产物变化只影响新交付；旧格式交付缺少冻结内容时要求重建，不做静默漂移。
- 可逆性：半可逆；旧交付需重建才能重新导出。

## D12 提案按基准基线校验，补答后重绑

- 决策：规则修订的完整性校验以提案 `base_baseline_id` 中的规则修订为准，而不是全局最新修订；补答阻塞问题时把问答写入提案约束并重绑需求修订/哈希。
- 理由：计划基线中的新修订不应阻塞另一项基于现行基线的需求；正常补答不应被误判为版本变化。
- 影响：多个计划基线可以并行存在；补答后的裁决使用新哈希，界面可继续处理。
- 可逆性：可逆。

## D13 声明支持 macOS 13+

- 决策：Electron 45 二进制实际 `minos` 为 13.0，安装包 `LSMinimumSystemVersion` 与文档统一改为 macOS 13+。
- 理由：原文档声明 macOS 12+ 与实际二进制不符。
- 影响：macOS 12 不在首版支持范围；Intel 未验证。
- 可逆性：可逆；降级 Electron 版本需重新验证。

## D14 交付导出非破坏性写入并冻结展示快照

- 决策：导出先在交付目录下的临时目录完整拼装、校验，成功后原子替换 `export/`；失败时保留上次成功导出，并记录 `last_export_error`。交付创建时同时保存 `display_snapshot`，包含产品、需求、基线状态与规则版本。
- 理由：旧格式重导曾在报错前删除最后一份历史成果；仅冻结文件也不足以阻止基线激活后静态站展示口径漂移。
- 影响：重导历史交付不会丢失已有的成功导出；历史交付始终显示交付时的 planned/current 状态；失败状态不再覆盖成功导出状态。
- 旧版交付没有 `display_snapshot` 时拒绝重导并保留原导出，不静默用当前记录重建展示。
- 可逆性：可逆；临时与备份目录在完成后清理。

## D15 Git 提交只消费用户选择的路径

- 决策：`gitCommit` 在 `git add` 后从所选路径的暂存差异中生成提交路径，并用 pathspec 提交；其他已预暂存文件保持暂存但不进入本次提交。
- 理由：仅修正状态解析仍无法阻止未勾选文件被一起提交，用户取消勾选必须等于不会提交。
- 影响：界面选择与提交范围一致；空目录或无可提交变更的所选路径不会造成 pathspec 错误。
- 可逆性：可逆。

## D16 保留现行规则时过滤被否决字段，保留显式约束

- 决策：keep 裁决的字段抽取不再读取原始需求；模型规格中的字段若只出现在被否决口径或现行规则的禁止子句中则移除。模型显式 `required`、设置开关值与选项默认值原样渲染，不再按位置覆盖。
- 理由：原实现会在保留现行规则后继续生成新增的身份证号等被否决字段；模板覆盖也错误呈现了模型规格。
- 影响：keep 产物仍显示允许字段；三字段全部 required 时第三项保持必填；关闭的开关显示关闭，A5 选中 A5。
- 可逆性：可逆。

## D17 已应用提案不因事后补答重新打开

- 决策：补答时若提案已应用或需求已有 decision_ref，只更新需求未知项与 resolved 分析的 `post_decision_answers`，不修改提案状态、哈希、基准或需求基线。
- 理由：已采纳并形成 planned 基线的需求，在补答非阻塞问题后被重新改成 pending，必然导致基准错位和 STALE_PROPOSAL。
- 影响：补答不会重开已应用提案；待裁决提案仍按既有逻辑重绑。
- 可逆性：可逆。

## D18 结构字段、旧交付快照与重命名提交的边界收口

- 决策：keep 字段过滤同时应用于 form fields、settings groups、list/board columns 与 demo_rows 键；settings 仅有 fields 时从 fields 构造分组并保留 `field.value`；规格规范化对重复 page.id 去重。
- 决策：缺少 `display_snapshot` 的旧交付拒绝重导并保留原导出；应用内列表使用冻结需求文档标题或「旧版交付」占位，不回退当前需求/基线。
- 决策：已应用提案的事后补答写入 resolved 的 acceptance/core_flows，将现有 artifacts 标记 stale；generated/reviewed 回到 analyzed 要求重新生成，delivered 保持历史交付冻结并提示新建需求。
- 决策：Git 提交从全部暂存差异中识别 rename/copy，按用户选择匹配新旧路径后双侧纳入提交，其他预暂存文件仍不提交。
- 理由：独立复验在非表单结构、0.1.1 形态旧交付、事后补答进入产物和 Git 重命名路径上复现了缺口。
- 影响：keep 的全称承诺覆盖主要结构；旧交付不会被当前记录静默重建；补答不再“看起来生效但产物未变”；重命名提交索引与工作区正确。
- 可逆性：可逆。

## D19 导出密钥扫描覆盖临时目录全部文本产物

- 决策：临时导出目录完成拼装后，递归扫描 `.html`、`.json`、`.md`、`.txt`、`.css` 文件；任一命中疑似密钥即抛错，不执行原子替换。
- 理由：只扫描 `index.html` 会漏掉原型、交互规格、需求文档与 CSS 规范；这些文件同样会进入交付包。
- 影响：命中时删除临时目录并保留上一次成功导出与 `exported` 状态，错误详情列出命中文件。
- 可逆性：可逆。

## D20 E2E 失败诊断与输入值断言

- 决策：三条旅程失败时写入 `failure.png` 与 `failure-diagnostics.json`；所有关键表单输入在写入后断言值，异常时重填一次。
- 理由：一次安装副本复跑在导入目录输入中少了最后一个字符；隔离复跑未发现应用侧路由或抽屉重渲染覆盖，输入丢字属于测试注入抖动。原失败处理只尝试截图，缺少控制台与页面状态，难以区分业务失败和输入问题。
- 影响：失败时可直接看到 URL、正文摘要、控制台输出与错误堆栈；输入注入抖动不会再被误报为业务失败。
- 可逆性：可逆。
