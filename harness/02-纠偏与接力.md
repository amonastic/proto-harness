# 纠偏与接力

本文件承载强纠偏、跨会话接力、历史对比和用户裁决覆盖规则，避免沿用错误结论或把被否定口径继续写入执行事实。

## 强纠偏与情绪升级重梳理

强纠偏触发信号见 `AGENTS.md#强纠偏信号重梳理红线`；本卷仅保留触发后的强制动作与输出边界。

### 强制动作

触发后必须立即执行以下动作，不得跳过：

1. 停止继续按原理解修改、总结或推进；若正在扩大改动，必须先暂停。
2. 重新梳理当前对话上下文，至少列出：用户已确认项、用户明确否定项、当前真正目标、本轮已改文件、可能越界或误改的位置。
3. 重新判断当前状态：继续修复 / 局部回退 / 先确认 / 暂停等待用户指令。
4. 强纠偏本身不是文件执行授权。用户骂“别问了 / 你没懂 / 谁让你改 / 怎么还这样”只能触发停手和重梳理，不能被解释成“赶紧直接改”。只有用户在同一轮或后续命中 `standards/授权词表.md` 定义的 L3 明确授权，才允许重新进入文件执行态。
5. 若需要继续修改，必须引用本轮授权原文，并重新输出修改范围、禁止范围、执行依据和验证计划；引用不出授权原文时，只能输出讨论、分析或待确认。
6. 本轮问题处理完后，主动询问用户：这次误解是否需要沉淀为 Harness 规则、执行者提示词或接力文档。

### 输出边界

- 不得把触发词当作业务事实、字段口径、权限口径或页面规则依据。
- 不得先道歉后继续沿用原错误方案；道歉不能替代上下文重梳理。
- 不得把该流程写成情绪安抚话术；核心动作是停止惯性执行、重建上下文、重新裁决下一步。
- 若用户在强纠偏后直接给出明确新指令，仍必须先完成最小重梳理，再按新指令重新判定状态。
- 最新用户消息优先于旧计划和旧授权。用户最新消息要求“先讨论 / grill / 审阅 / 怎么优化 / 你没懂 / 谁让你改”时，必须切回非文件执行态；不得因为前文曾经授权“落文档 / 执行”就继续改文件。

## 握手失效与规则漂移

完整定义见 `AGENTS.md#对话称呼握手规则`；握手失效时旧记忆只能作线索，必须补齐当前读取、授权、范围和验证证据。

## 跨会话事故复盘与接力准入

当用户提到“其他模型跑偏”“几个会话已经破防”“执行者没按 Harness”“接力后误解”“上一位 AI 结论不可信”等跨会话问题时，必须先进入事故复盘与接力准入，不得直接把上一位 AI 的结论、接力文档、执行者最终回复或历史审阅当作当前事实。

### 触发后的最小动作

1. 先停止发包、停止页面/抽屉/规则修改，除非用户明确要求本轮只修 Harness 或只落事故报告。
2. 输出事故卡，至少包含：用户已确认项、用户明确否定项、执行者声称项、已由本地文件或命令验证项、未验证项、当前真正目标、禁止继续假设项、建议下一步。
3. 若接收了接力文档、上一位 AI 回复、历史审阅或执行者交付，必须先做接力材料分层：`用户已确认` / `执行者声称` / `本地已验证` / `未验证` / `已废弃或用户否定`。
4. `执行者声称` 与 `未验证` 只能作为线索，不得写入真实页面、需求抽屉、接口口径、权限口径或 `design over` 结论。
5. 若用户已经明确否定某口径，该口径必须进入 `已废弃或用户否定`，后续不得再作为待确认项、默认方案或旧口径保留。
6. 若任务是“误执行残留 / 回退历史布局 / 恢复旧 UI / 剔除误改”，必须先列出误改项保留矩阵：应回退的页面结构、应保留的全局能力资源、仅机械更新的缓存版本号、受影响入口、验证方式。主题切换、全局脚本、公共 CSS、抽屉能力、入口路由等跨页面能力不得因页面布局回退而整包删除；确需移除时必须有本地证据和用户确认。
7. 若任务要求比较历史版本、瘦身前后、旧规则或文件是否存在，必须先建立 git 证据链：用 `git log --follow -- <path>` 查文件演进，用相关提交的 `--name-status` 查新增/删除/重命名，用 `git merge-base --is-ancestor` 或等效方式确认提交祖先关系。若旧规则被拆到多个文件或工具适配层，必须按规则主题建立矩阵，而不是只做同名路径 diff。单个 `git show <commit>:<path>` 失败只能说明该路径在该提交不可读取，不能直接推导“文件不存在”“一直没有”或“规则已丢”。
8. 需要继续执行时，必须重新完成强制执行闸门；不能沿用上一位 AI 的开工声明、验证结果或“已读规则”。

## 用户纠偏口径收口

当用户逐条回复执行者的“待确认项 / 疑问项 / 修改结果 / 已完成说明”时，这些回复不是普通建议，而是当前执行优先级最高的口径裁决。AI 必须把用户纠偏先结构化，再进入任何页面或抽屉修改。

### 触发信号

- 用户说执行者“改乱了”“没按我的要求”“说改好了但不对”“待确认我已经回复过了”。
- 用户逐条给出“默认是 / 错误 / 需要 / 不需要 / 允许 / 不允许 / 禁止 / 维护了什么就是什么”等裁决。
- 用户指出某些内容不该再作为待确认项，或要求减少对开发、测试无价值的废话。

### 强制纠偏矩阵

继续执行前必须先输出并自查以下矩阵：

```text
用户纠偏矩阵：
用户原话：
应落口径：
旧错误口径：
影响文件：
影响 docId 或页面：
需要删除的待确认项：
需要同步的页面/抽屉/右侧说明：
验证方式：
```

### 写入规则

1. 用户明确裁决的内容必须从 `待确认项` 移出，写入对应字段、规则、边界或操作条目；不得继续写“待确认 / 建议确认 / 需后端确认”。
2. 用户明确否定的旧口径必须从当前有效正文中移除或改写为正确口径，不得保留成“旧口径 / 兼容说明 / 仍需确认”。
3. 纠偏涉及同一业务对象的多处说明时，必须同时核对页面正文、右侧控制区说明、内联 `DocPanel`、模块 `js/docs.js`、公共 `doc-builder/doc-panel`、`需求文档.md` 和入口页说明；只改一处不得交付。
4. 用户明确“不需要”的校验、确认、提示、交互或待确认项，不得由 AI 因规则惯性重新补回；若仓库规则要求二次确认但用户本轮明确排除，必须输出冲突裁决，由用户裁定，不能暗中写回。
5. 用户明确“允许”的业务场景必须正向写清作用域和既有逻辑边界，例如“同一标识允许跨站点创建；唯一值按既有逻辑判断”，不能只写“按既有逻辑判断”。
6. 用户明确“维护了什么就是什么”时，不得再写脱敏、格式替换、默认补值或模拟展示；如列表空间有限，只能另写溢出截断规则，且不能改变字段真实展示值。
7. 需求抽屉正文禁止直接出现 `placeholder`、`tooltip`、`mock`、`todo`、`modal`、`dialog` 等技术或英文占位表达；需要描述时改成中文业务口径，例如“搜索框默认提示文案”“确认弹窗”。
8. 对弹层、页面标题、基础控件等成熟页面已有内容，需求抽屉只写本页差异和必要业务规则；不得重复堆页面结构、标题、按钮位置、基础打开关闭流程等低价值说明。
9. 用户明确入口、页面或业务对象作用域后，旧页面、旧抽屉或执行者残留的更大作用域不得反向覆盖用户裁决；必须把旧口径标为已废弃或用户否定，并从当前有效页面、抽屉和说明中清理。例如用户确认“站点业务开关进入单个站点客户列表”后，不得继续沿用“多站点勾选 / 批量设置 / 已选站点 / 多站点写入 / 失败站点列表”作为需求事实。
10. 最终回复必须逐条对应用户纠偏项说明处理结果，至少区分：已修正、已删除旧口径、未修正及原因、仍需用户确认的问题。
