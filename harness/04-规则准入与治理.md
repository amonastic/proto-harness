# 规则准入与治理

本文件承载规则写入准入、规则资料地图、结构化标准、skill 路由和治理边界。

## Harness 准入机制

任何新建、修改、扩展、压缩或迁移 harness 的任务，都必须先通过本机制；未完全满足准入条件时，不得写入 `AGENTS.md`、本文件、`DEVELOPMENT.md`、`standards/*`、skills 或其他规则文件，只能输出审查结论、缺口和建议补强方向。

本机制用于判断“某段规则是否值得进入 harness”，不是用于包装已经写好的内容。不得先写入再补准入说明。

### 准入结论

准入结论只允许三种：

- `允许写入`：所有必备项均满足，且写入位置、边界、验证方式清楚。
- `需确认后写入`：规则方向成立，但仍缺少影响范围、归属层级、冲突裁决或用户确认。
- `禁止写入`：规则过窄、过虚、重复、无依据、会制造平行入口，或会把具体业务案例固化成通用规则。

只有 `允许写入` 可以进入文件执行态。`需确认后写入` 和 `禁止写入` 都不得修改规则正文。`需确认后写入` 必须只剩一个明确阻塞项，并写清需要用户确认的具体问题；若存在多个阻塞项、阻塞项无法一句话问清，或缺口可通过继续查文件补足，应先继续审查或判定为 `禁止写入`。

准入通过不等于可以直接落笔。`允许写入` 后仍必须继续执行本文件的强制执行闸门、开工声明、执行前审查、最小修改和完成后自查。

### 沉淀 ROI 评分（触发词自动进入）

当用户说出「沉淀」「沉淀规则」「沉淀到 harness」等触发词并拟向 `AGENTS.md`、`harness/*`、`DEVELOPMENT.md`、`standards/*` 或 skills 写入规则时，在准入审查通过后、落笔前，必须先输出 ROI 评分卡：

```text
沉淀 ROI 评分卡：
复发成本：<不沉淀该规则，同类问题多久复发一次、每次返工代价>
执行成本：<每轮任务的前置增量：读几个文件、几秒>
检索成本：<对规则文件膨胀度的影响：新增几行、是否新文件、是否降低既有规则命中率>
ROI 结论：<高 → 完整写入 / 中 → 简化后写入（说明删了什么）/ 低 → 单条合并入既有章节 / 不沉淀>
```

分级处理：

- `高`：按方案完整写入。
- `中`：先降级再写入；降级方式优先「合并进既有章节的 1-2 条」，其次「压缩为单句」，必须在报告中写明删减内容。
- `低`：默认不沉淀；若与既有规则高度重复，只允许以一行引用方式合并，禁止重写正文。
- 四个字段任一留空、只写「已评估 / 无问题 / 影响不大」，视为空跑失败，不得写入（同 `harness/01-强制闸门.md` 闸门空跑失败口径）。

边界：本规则只作用于项目内 harness/standards/skills 写入；用户说「沉淀到 Obsidian / Shane's Cortex」时走对话蒸馏硬闸门，不触发本节。

### 写入类型分流

不同类型的 harness 变更门槛不同：

- 新建：必须证明现有章节无法承载，列出至少两个候选归属位置及放弃原因；否则禁止新建。
- 修改：必须定位原章节、原规则缺口和最小改动点；不得借修改重写整节。
- 扩展：必须说明新增约束补足了哪类缺口，且不会扩大到无关任务类型。
- 压缩：必须列出被合并、删除或改写的原规则，并证明语义未丢失。
- 迁移：必须说明迁移前后入口、引用关系和优先级变化，不得造成双入口并存。
- 删除：必须证明规则已失效、重复或被更高优先级规则覆盖，并说明删除后的替代读取路径。

### 必备准入项

每次写入 harness 前必须逐项检查：

1. 问题来源：说明它解决的是哪类重复发生的问题，依据来自用户明确要求、仓库规则冲突、历史执行失败、审查发现或成熟页面实践；必须给出可追溯证据定位，例如用户原话、文件路径、章节、行号、命令输出摘要或具体失败现象。
2. 适用范围：说明适用于哪些任务类型、页面类型、文档类型或治理场景，不适用于哪些场景。
3. 归属层级：确认应进入 `AGENTS.md`、`harness/*`、`DEVELOPMENT.md`、`standards/*`、skill，还是只应留在业务需求中；至少比较两个候选归属位置，说明采用和放弃原因，不得新增平行入口。
4. 抽象程度：规则必须脱离单一业务案例，能覆盖一类问题；业务案例只能作为临时说明，不得成为规则主体。
5. 可执行性：必须包含触发条件、读取对象、判断步骤、输出格式或禁止行为，不能只写“注意”“认真检查”“保持一致”。
6. 证据边界：必须说明哪些结论有依据，哪些仍是推断或待确认；不得把未确认口径写成事实。
7. 冲突检查：必须对照 `AGENTS.md`、本文件、`DEVELOPMENT.md`、相关 `standards/*` 和现有成熟页面，输出冲突矩阵；不能只写“未发现冲突”。
8. 最小写入：优先增量补充现有章节；不得为了一个局部问题重写整章、拆出新规则文件或迁移规则体系。
9. 验证方式：必须说明写入后如何验证，治理文档至少运行 `git diff --check`；涉及页面、抽屉、脚本或标准审计时按对应命令补充验证。新增规则文件（含 skills 的 SKILL.md 与 archive 过程材料）必须同轮登记 `standards/rule-map.json`，未登记即视为准入未收口；镜像 skill 同步登记对应 mirrorGroup。
10. 反例压测：至少列出两个不该触发该 harness 的场景，说明如何避免误伤或过度套用。

### 硬失败条件

出现以下任一情况，即使模板其他字段已填写，也必须判定为 `禁止写入`：

1. 没有证据定位，或证据只写成“历史经验”“感觉需要”“之前出过问题”。
2. 没有候选归属比较，无法证明为什么写入当前文件和当前章节。
3. 没有冲突矩阵，或未明确读过相关规则文件。
4. 没有反例压测，无法说明不适用场景。
5. 没有写入后复审方式，只写了命令校验。
6. 准入审查由结论倒推，字段只是为“允许写入”补材料。

### 禁止写入情形

出现以下任一情况，直接判定为 `禁止写入`：

1. 只是把某一次具体需求、字段、状态、枚举或业务案例复制成通用规则。
2. 只有结论没有流程，无法指导下次 AI 如何读取、判断、输出或拒绝。
3. 只表达价值观或口号，例如“更严谨”“更完整”“避免问题”，但没有可检查动作。
4. 与既有规则重复，且不能说明新增规则补足了什么缺口。
5. 会削弱 `AGENTS.md` 唯一主入口地位，或让任一 Harness 分卷变成新的主规则入口。
6. 会鼓励讨论态直接改文件、无依据写业务事实、把需求说明塞进真实页面、或绕过静态原型边界。
7. 未说明不适用场景，导致局部经验被全局滥用。

### 写入前输出模板

任何 harness 写入前，必须先输出：

```text
Harness 准入审查：

证据定位：
适用范围：
不适用范围：
归属层级：
候选归属比较：
抽象程度：
可执行性：
证据边界：
冲突矩阵：
反例压测：

```

若准入结论不是 `允许写入`，下一步只能是补证据、改方案或等待用户确认，不能修改文件。

写入后复审必须重新阅读最终文本，检查是否出现口号化、重复规则、具体业务污染、入口层级漂移、误伤无关任务、或与准入审查不一致；复审不通过时必须继续修正或回退新增内容。

## 业务外脑沉淀判断

本节只规定“是否应该提示用户沉淀到外部业务知识库（业务外脑）”的判断流程，不授权自动写入外部知识库，也不替代对应的蒸馏写入协议。业务外脑位置由 `governance.config.json` 的 `businessBrain.root` 声明（或 `BUSINESS_BRAIN_ROOT` 环境变量覆盖），本文件不承载任何本机绝对路径。

### 触发场景

出现以下任一情况，AI 必须在收口时判断是否值得沉淀到业务外脑：

- 业务需求访谈已经闭环，形成稳定业务对象、角色、端范围、权限、配置、状态流转或前后端影响口径。
- 需求页面、需求抽屉、需求文档或开发任务包已经落地，并包含可复用业务规则，而不是一次性 UI 实现。
- 用户在沟通中确认“默认就是 / 一般来讲 / 以后可以默认 / 这种情况通常”等业务规律。
- 用户纠正了 AI 对业务域、角色、端范围、流程、状态或配置影响的理解。
- 同类业务判断在多次需求、多个页面或多个文档中反复出现。

### 必读材料

判断前必须读取业务外脑根目录（`businessBrain.root`）下的入口与规则文件：

1. `00-大模型入口.md`
2. `01-业务知识抽取标准.md`
3. `02-对话沉淀规则.md`
4. 若用户确认写入，再读取使用方知识库自身提供的对话蒸馏/写入协议文件

无法读取任一必读文件时，必须说明失败原因，并把沉淀判断降级为待确认；不得声称已按业务外脑规则判断。

### 判断矩阵

输出判断时使用以下结构：

```text
Obsidian 业务外脑沉淀判断：
结论：建议沉淀 / 暂不沉淀 / 待确认
候选知识：
建议状态：candidate / confirmed / pending
依据：
适用范围：
不适用范围：
目标目录或候选文件：
不写入内容：
需要用户确认：
```

### 可沉淀内容

- 业务能力、业务对象、角色、权限、端范围、配置项、状态流转。
- 可帮助后续判断一个需求应该涉及哪些端、前端、后端、接口、权限、配置或数据存储的规则。
- 用户明确确认过的默认业务口径。
- 多个页面、需求文档或对话反复出现的业务规律。
- 某类功能的默认多端联动关系或典型例外。

### 不沉淀内容

- 纯 UI 风格、颜色、字号、间距、页面壳、视觉基线和一次性页面排版。
- 项目执行规则、`AGENTS.md`、Harness、`DEVELOPMENT.md`、`standards/*`、脚本命令、审计命令和工具适配规则。
- 单次设计稿实现细节、演示 mock、临时文案、当前任务专属排版。
- 模型为了完成任务临时做出的推断。
- 敏感信息、账号、密钥、token、cookie、原始聊天全文或附件原文。

### 写入边界

- 未经用户确认，只允许输出判断和候选知识摘要，不得修改业务外脑。
- 用户只说“可以先放 / 先记着”时，默认 `candidate`。
- 用户明确说“这是长期规则 / 以后默认这样 / confirmed”，或有多来源证据时，才允许标为 `confirmed`。
- 若内容属于 AI 协作、Harness、Prompt 或多模型规则，不写入业务外脑，应按使用方的 AI 协作协议类目录方向重新判断。
- 若只更新项目仓库报告或任务清单、不写入业务外脑，最终回复必须说明原因。

## 规则 JSON 运行图

AI 执行页面、抽屉、文档或治理任务时，必须把 `standards/*.json` 当成结构化约束源，而不是只读自然语言说明。

| JSON | AI 使用方式 | 主要约束对象 |
| --- | --- | --- |
| `standards/design-tokens.json` | 建立视觉基线，不自行发明颜色、圆角、间距、状态色和图标尺寸 | 色彩、字号、间距、圆角、按钮、卡片、状态语义、图标 |
| `standards/platform-rules.json` | 判断页面所属端与页面骨架，决定 Web / App / 小程序默认抽屉策略 | 平台入口、列表页、详情页、模块页、开发模式 |
| `standards/ui-spec.json` | 驱动页面登记、模板边界、抽屉默认模式、文档入口和 token 机检 | 页面注册、导航边界、`DocPanel.autoShow`、`dg-doc-btn`、`variables.css` |
| `standards/ui-consistency-rules.json` | 驱动一致性审计，检查抽屉、CSS 规范、图标、状态标签和设计稿控制文案 | 需求抽屉、CSS 规范 Tab、图标来源、状态文案、开发备注 |
| `standards/doc-spec.json` | 驱动需求抽屉与需求文档写作、结构、版本标记和文档审计 | 抽屉正文、`需求文档.md`、静态原型边界、迭代同步对话框 |
| `standards/module-spec.json` | 判断模块声明字段、开发模式、轻量抽屉结构和模块级交付策略 | 模块元数据、模块 docPanel 模式、页面类型、共享组件 |
| `standards/page-baseline-spec.json` | 控制复刻改造边界，保护既有字段、动作、状态和信息结构 | `clone-source`、`change-type`、safe-add、版本高亮 |

执行时的默认读取顺序：

1. 先读 `AGENTS.md` 判定讨论态、执行态、排障态或治理态。
2. 再按任务对象读取相关 JSON：页面先 `ui-spec` / `platform-rules`，视觉先 `design-tokens` / `ui-consistency-rules`，文档先 `doc-spec`，复刻先 `page-baseline-spec`，模块先 `module-spec`。
3. 修改前用 JSON 反查“该组件受哪些规则约束”，不要只凭成熟页面肉眼判断。
4. 修改后运行对应命令，并区分硬失败、审计报告问题和人工边界问题。
5. 需要统一风格时，先取最新迭代索引做 7 分基准，再用历史优秀 UI 做 3 分收口，不要先看感觉后找证据。

不要把 `ui-spec.json` 的 `checks.pages` 全量内容复制到人类文档；它是登记清单，不是阅读手册。

优先级冲突时，按下面口径处理：

- `visual-tightening` 与主规则里常写的 `visual-tighten` 视为同类口径，执行时以 `page-baseline-spec.json` 的 `visual-tightening` 为准。
- 只要同一项在 JSON 与 markdown 主规则中出现冲突，优先读 `AGENTS.md` 和专项 JSON 的当前约束，不把历史 token 当成当前执行事实。

## Skill 路由

| 任务类型 | 优先 skill | 目的 |
| --- | --- | --- |
| 判断方案、取舍、规则口径 | `independent-judgment` | 防止顺着错误前提执行 |

| 页面、抽屉、文档、规则、脚本修改前 | `design-task-preflight` | 检查任务类型、依据、缺口、冲突和越界风险 |
| bug、脚本失败、页面异常 | `engineering-diagnose` | 建立可复现反馈环后再修 |
| 修改完成后 | `implementation-self-audit` | 自查范围、边界、规则和校验 |
| 文档和知识收口 | `neat-freak` | 清理重复、过期、冲突信息，面向交接 |
| PPT、演示视频、投标展示、设计方向探索 | `huashu-design` | 作为外部设计产出能力，生成 HTML deck、动画、视频或视觉探索稿 |

`AGENTS.md` 中提到但当前工具环境不可用的 skill，必须在开工声明中说明不可用，并使用最接近的可用 skill 替代；不得因 skill 名称不可用而停止执行或假装已使用。当前常见替代口径：

- `ai-context` 若可用则用于规则体系判断；不可用时，用 `independent-judgment` + `engineering-zoom-out` 覆盖。
- `project-overview` 若可用则用于目录与结构梳理；不可用时，用 `engineering-zoom-out` 覆盖。

### 外部设计能力 skill 接入边界

`huashu-design` 仅作为 PPT、演示视频、投标展示、视觉方向探索、独立宣传动画和高保真展示稿的外部设计能力使用；它不替代本项目的主规则入口、页面执行 Harness、抽屉规则、静态原型边界和成熟页面复用要求。

使用前必须先按 `AGENTS.md` 判断任务状态：

1. 若任务目标是正式 Web 管理端、移动作业端或小程序端页面、需求抽屉、CSS 规范、迭代索引、规则文档或脚本，仍优先走本项目 `design-task-preflight`、`DEVELOPMENT.md` 与相关 `standards/*`；`huashu-design` 只能作为视觉参考或单独产出辅助。
2. 若任务目标是 PPT、HTML deck、演示视频、GIF/MP4、投标展示素材、独立视觉探索或方案路演，可以触发 `huashu-design`；触发时必须声明其为外部设计能力，项目规则优先级不变。
3. `huashu-design` 的 assumptions、placeholder、reasoning、场景切换器、设计顾问说明、演示控制项，不得写入正式页面正文、业务弹窗、业务抽屉或需求抽屉正文；如需保留，只能放在独立展示稿、演示页或右侧独立控制区。
4. 涉及具体品牌、产品、人物、院校、地址、版本、发布时间或规格参数时，必须先按事实验证规则查证来源；查不到时标为 `待确认`，不得把外部 skill 的推断写成本项目事实。
5. 交付物若用于线上手动上传，仍按本项目手动上传缓存规则列出全部文件；若只生成本地 PPT、视频或截图，最终回复列出本地生成文件和未上传状态。
6. 完成后至少运行与交付物匹配的最窄验证：HTML 展示稿优先用浏览器或 Playwright 截图检查，视频/GIF 优先检查文件存在、时长和首帧/关键帧，治理文档变更至少运行 `git diff --check`。

## cc-sdd 使用边界

`cc-sdd` 是候选规格驱动流程，不是本仓库当前默认执行链路。

适合使用 `cc-sdd` 的情况：

- 要把一个大需求拆成正式 spec、requirements、design、tasks。
- 需要长期自主实现，并接受阶段审批和任务边界管理。
- 明确希望启用 Kiro 的专用目录结构（当前未启用，目录不存在）。

不建议直接使用 `cc-sdd` 的情况：

- 只是整理当前规则和项目资料。
- 只是页面微调、抽屉文案修正、入口注册、机检修复。
- 仓库内已有规则能直接判断和执行。

若未来确认接入，建议路径：

1. 先用本 harness 梳理仓库规则、资料地图和执行边界。
2. 再运行 `cc-sdd` 的 Codex skills 安装模式。
3. 把本仓库规则映射进启用后的 Kiro steering，只放引用和项目边界，不复制整份规则。
4. 对第一个大需求试跑 `/kiro-discovery`，由它决定是否创建单 spec、多 spec 或直接实现。

## 规则冷宫治理

规则冷宫采用「物理移出 + 原位指针」形态，用于降低日常检索成本：低频规则正文整体搬迁至 `harness/cold-storage.md`，原文件位置只保留一行指针（如 `N. {规则名} → 已归档 cold-storage#rN（命中「{主题}」任务时读取）`）。纯标记或清单式冷宫不减少每轮读取量，禁止使用。

1. 白名单永不入冷宫：`harness/00-执行总入口.md`、`harness/01-强制闸门.md`、`harness/02-纠偏与接力.md` 全文，以及 `AGENTS.md` 红线章节（T0/T-1、强纠偏、授权、握手、状态判定）。
2. 移出与搬回都必须用户人工批准；AI 与定时任务只产出候选清单，无写入权限。
3. 每周五 18:00 定时任务（`npm run audit:rules-usage`，crontab 触发）读取 `.harness-runtime/rule-usage/*.jsonl`，统计各规则章节引用频率，对照白名单输出「冷宫候选清单」（章节锚点、本周与近 4 周引用次数、建议），报告写入 `doc/平台治理/规则频率审计/audit-YYYY-Www.md` 并弹系统通知，停止等待人工裁决；无数据时报告「本周无统计」即可结束。
4. 冷宫条目必须记录：原文件与行号区间、移出日期、移出原因、释放条件；释放时把正文搬回原位并删除指针行。释放属于 harness 修改，须按本文件准入机制与开工声明执行，完成后运行 `git diff --check` 并确认指针行已删除、正文位置与归档前一致。
5. 统计周期不足 4 周的数据只能标注「观察中」，不得直接产出移出建议。

### 镜像整覆盖红线

整文件覆盖式同步镜像（canonical → mirror，如 `AGENTS.md` → `.codebuddy/rules/*.mdc`）前，必须先用 `git diff` 或 `git show HEAD:<旧mirror>` 核对被覆盖内容中是否存在 canonical 没有的独有信息；确认无独有内容（仅为陈旧残留）后才允许整覆盖。先覆盖后验证属顺序倒置，若旧镜像独有规则被静默丢弃，视为不可逆事故。

## 目录命名治理边界

目录和文件命名治理采用“新文件准入、旧文件分批治理”。新增页面、文档、需求说明、快照、图片、下载模板和脚本前，必须确认所属端、模块、迭代和页面类型，并复用现有同类命名风格；无法判断时标为待确认。

普通需求不得顺手批量改旧目录名、页面名、快照路径或入口路径。涉及 `index.html`、`迭代索引`、`snapshots`、`docs.js` 或线上上传路径的改名，必须单独立迁移任务，先输出治理清单和影响分析，再运行入口与快照审计。
