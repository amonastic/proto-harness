# 页面与抽屉执行

本文件承载页面、抽屉、组件、业务逻辑、design over、故障排查和 TAPD 查询等任务分流规则。

## 视觉改动前强制三查

任何涉及页面视觉、样式、按钮、状态组件、抽屉正文或 CSS 规范 Tab 的修改，动手前必须先完成三项检查；任一未完成即视为违反本规则，不得声称已按成熟风格执行：

1. **查成熟页**：先在同一端或同模块目录搜索并读取 1-2 个成熟页面，记录其组件形态（按钮 / 标签 / 胶囊 / 图标 / 表格）与尺寸基线；若目标对象是需求文档按钮，必须复用 `.tools` 右侧工具列范式（如 `field-app/main/pages/设备详情.html`），禁止自创 fixed 视口定位或独立悬浮样式。UI 设计类任务命中后，按 `doc/UI-设计工作流.md` 对应场景（澄清/设计/实现/审查/修复）执行 skill 链。
2. **查规则**：读取 `standards/ui-consistency-rules.json`（图标 / 按钮 / 阴影 / 状态标签）与本节 `CSS 规范 Tab 审核与修复`；命中「颜色规范必须色块」「主按钮禁止投影」「按钮纯文字或纯图标」等既有规则时直接执行，不得自创。
3. **查实值**：CSS 规范 Tab 中的所有颜色、字号、圆角、间距、按钮高度必须与当前页面 computed style 或源码真实值一致；禁止写历史旧值、规划值或推断值。完成后运行一次浏览器截图或 DOM 查询核对。

若本轮为纯新增且用户已明确给出精确值（如「12px / 400 / padding 2px 9px」），则第 1、2 项可降级为「已按用户给定值执行」，第 3 项仍须核对该值确实生效。

反例：用户明确说「完全照抄截图 1:1」，此时三查降级为按图执行，但第 3 项实值核对仍保留；用户只是问「能不能」，进入分析态，不触发三查。

## 成熟基准与加权判定

需求抽屉成熟基准以 `standards/doc-spec.json` 为准；本节只保留按平台选择复用来源和加权执行的方法。

执行页面、抽屉和视觉收口时，不是随机挑一个“看起来成熟”的页面，而是按平台先选基准，再做加权吸收。

### 先选基准，再谈统一

| 平台 | 主要基准 | 统一方式 |
| --- | --- | --- |
| Web | `admin-portal/store-admin/index.html` + `admin-portal/store-admin/js/docs.js` 中的结构化 `card-list` 抽屉 | 0-1 后台页面先对齐管理后台成熟列表页抽屉的组织方式、字段颗粒度和边界写法 |
| App | `field-app/main/pages/投递统计.html`（示例成熟页） | 抽屉写法优先对齐统计页的分节颗粒度，再用最新迭代索引的分组方式统一页面索引层级 |
| 小程序 | `mini-program/main/pages/下单.html`（示例成熟页） | 以成熟页提供入口组织、首页布局和字段级规则样本，合并成一套小程序轻量页基准，不拆成多套平行口径 |

移动作业端风格例外：当目标路径属于移动作业端（如 `field-app/main`）时，页面风格基线优先读取 `harness/rules/风格基线-移动作业端.md`，并使用该文件列出的成熟页面作为 style clone-source。上表 App 基准继续服务其他 App 场景；不得用该专项基线覆盖其他端。

### UI 加权规则

- 最新迭代索引占 `7` 分，历史优秀 UI 占 `3` 分。
- `7` 分负责：页面结构、信息层级、入口顺序、状态组织、抽屉分节顺序。
- `3` 分负责：卡片质感、间距收口、按钮密度、标题节奏、局部视觉完成度。
- 这不是把 CSS 数值机械平均，而是先用最新迭代定方向，再用历史优秀 UI 收紧表现。
- 如果两者冲突，结构和流程优先服从最新迭代，视觉收口优先参考历史优秀 UI，但不得突破 `AGENTS.md` 和专项 JSON 的当前规则。

## 组件路由

| 改动对象 | 必读规则源 | 重点检查 |
| --- | --- | --- |
| 页面入口、导航、页面类型 | `ui-spec.json`、`platform-rules.json`、`page-type-guide.md` | 是否登记、是否误带 `system-nav`、是否属于平台入口/迭代索引/模块页 |
| 需求文档按钮和抽屉 | `ui-spec.json`、`ui-consistency-rules.json`、`doc-spec.json` | `dg-doc-btn`、`doc-panel.js`、宽度 `780px`、Web 默认关闭、App/小程序默认打开 |
| CSS 规范 Tab | `ui-consistency-rules.json`、`doc-spec.json` | 是否支持 `getDocCssContent(docId)`，是否有颜色/字体/圆角/间距结构和可视化能力 |
| 真实页面正文 | `doc-spec.json`、`ui-consistency-rules.json` | 不得出现需求说明、版本摘要、开发备注、测试提示、模拟操作和设计稿专用文案 |
| 视觉样式 | `design-tokens.json`、`ui-consistency-rules.json` | 是否引用 `variables.css`，是否复用 token、状态色、圆角、间距 |
| 图标与状态标签 | `design-tokens.json`、`ui-consistency-rules.json` | 图标来源是否允许，状态文案和颜色是否同模块一致 |
| 需求文档正文 | `doc-spec.json`、`module-spec.json` | 章节是否齐、版本标记是否内联、是否避免“应该是/看情况”等漂移表达 |
| 复刻改造 | `page-baseline-spec.json`、`doc-spec.json` | 是否声明 `clone-source`、`change-type`，safe-add 是否越界新增筛选/统计/快捷入口 |
| 模块元数据 | `module-spec.json`、`ui-spec.json` | 模块字段是否齐，平台枚举是否为 `web/app/miniapp`，doc 交付策略是否匹配 |
| 迭代同步虚拟目录 | `doc-spec.json`、`DEVELOPMENT.md` | 是否使用 `同步 · {端名}`，是否只做虚拟目录和对话框，不新建页面 |
| 迭代索引导航菜单 | `ui-consistency-rules.json` | 菜单项统一 14px，仅分组标题有字号区分（一级 11px、二级 10px）。二级分组按平台端拆分（作业端 App / 用户端 App / 管理后台 / 运维后台 / 用户小程序 / 设备端 App）；菜单项名称只写页面名，不带端名后缀，端名由分组或二级子组标题承载（`pageNames`、面包屑、overview 卡片链接不受此限）；当单个 App 仅 1 个菜单项时可合并用"移动端"。同步目录项置于所属分组末尾 |

### 需求抽屉正文样式生效审核

当用户要求新增、修改或排查需求抽屉正文时，必须同时审核正文结构和样式生效情况，不能只检查文案是否完整或抽屉是否能打开。

1. 先定位抽屉正文数据源：页面内联 `DocPanel`、模块级 `js/docs.js`、公共 `doc-builder`、`doc-panel.js` 或 `需求文档.md`；不得凭页面截图直接改样式。
2. 再定位成熟复用源：优先复用同端、同组件、同数据结构的成熟抽屉正文；Web 端可优先对照管理后台 card-list 类结构化抽屉，App / 小程序按 Harness 成熟基准选择参考。复用源必须写入 `clone-source`。
3. 修改前必须输出“抽屉执行矩阵”，逐页列出：目标页面、正文数据源、按钮/外壳数据源、成熟复用源、目标 docId、当前结构类型、计划采用的结构类型、禁止写入内容、验证方式。未输出矩阵不得修改抽屉正文。
4. 必须区分“抽屉外壳接入”和“正文结构达标”：`doc-panel.js`、`DocPanel.toggle/autoShow`、抽屉宽度、按钮位置只能证明外壳可用，不能证明需求抽屉已符合规范。正文仍必须对照成熟源检查分区、规则卡、表格、版本标签和边界分区。
5. 当成熟源为管理后台 `card-list` 或同类结构化抽屉时，正文优先复用其结构颗粒度：`docSection` / `buildRequirementDoc` 思路、`doc-rule-card`、`doc-rule-line`、`doc-plain-table`、`doc-section-danger`。不得只把普通 `h3 + ul + table` 包进公共抽屉后宣布完成。
6. 字段密集型说明（例如筛选字段、表单字段、导入字段、列表字段）不得把字段逐个拆成纵向大卡片，也不得把 5 条以上长规则塞进同一个 `doc-rule-card` 里形成“大卡片 + 两列长句”。默认优先用 `doc-plain-table` 或 `buildRequirementDoc` 的 `filterRows` / `fieldRows` 做紧凑表格；同一功能动作下确实需要动作、结果、接口、边界时，才使用 `actionGroups` / `doc-rule-card`。
7. 若执行者无法判断如何组织字段密集型说明，兜底参考迭代索引中成熟列表页（如 `迭代索引/202606下.html?page=demo-card-list`）0-1 需求说明区的格式：筛选项集中为表格行，字段说明集中为表格行，操作能力才分组为规则卡。该参考只作为抽屉组织结构样式，不代表业务字段可照搬。
8. 正文必须使用能被抽屉样式覆盖的语义结构：标题用成熟页同级标题节点，列表用 `<ul>` / `<ol>` + `<li>`，规则块、表格、代码标签、版本标签使用现有成熟结构或渲染层支持的结构。
9. 禁止使用裸 `•`、纯换行文本、连续 `<br>`、未闭合列表、散落标签，或只靠大段 utility class 拼出正文样式；这类写法会导致部分样式生效、部分样式失效。
10. 需求抽屉正文不得写入执行者备注或原型实现限制，例如“不要覆盖控件”“不符合线上布局”“只展示步骤头”“不实现真实上传/解析/预览/下载”“测试提示”“开发备注”。这些内容只能进入执行计划、开发文档或待办，不得进入正式页面需求抽屉。
11. 若出现标题生效但列表、段落、表格或标签不生效，优先按正文 DOM 结构、抽屉 CSS 覆盖范围、渲染层转换能力排查，不得先堆全局 CSS、通配式 `border/background` 或重写抽屉组件。
12. 修复顺序为：对齐成熟页正文组织结构 → 修正语义标签与闭合关系 → 复用已有正文 class / 渲染结构 → 必要时补最小局部样式。不得顺手改业务规则、页面真实正文或其他 Tab。
13. 完成后必须按“抽屉硬失败清单”逐页自查，任一命中即不得交付：未定位正文数据源；未声明成熟复用源；只改外壳未改正文结构却称完成；仍是裸 `h3 + ul + table`；字段密集型说明被拆成一字段一卡片，或仍用单个大卡片承载多条长句；缺少规则卡或结构化表格；存在执行者备注、测试提示、开发备注或原型实现限制；同一需求跨端章节骨架无理由不一致；旧口径否定语反复出现；CSS 规范 Tab 被破坏或未说明沿用。
14. 完成后必须人工打开目标抽屉，对照成熟抽屉检查标题、段落、列表、表格、规则卡、版本标签、边界分区和 CSS 规范 Tab 是否都按预期渲染；脚本通过不能替代这一步视觉复核。无法浏览器复核时，最终回复必须明确“未完成视觉复核”和原因。
15. 最终回复必须说明本次对齐的是“外壳组件”“正文组织结构”还是两者都包含；若只完成外壳接入，必须明确标注正文结构仍待对齐，不得含糊写成“抽屉样式已修复”。
16. 生成抽屉正文 HTML 后必须自查语义合法性。禁止 `<p>` 内包裹 `<ul>`、`<ol>`、`<div>`、`<table>`、`<pre>`、`<section>`、`<article>`；禁止 `<span>` 内包裹块级元素；禁止 `<li>` 脱离 `<ul>` / `<ol>`；禁止 `<td>` / `<th>` 脱离 `<tr>`。命中任一项时，先修 HTML 结构，再复核样式。

### CSS 规范 Tab 审核与修复

当用户要求检查或修复需求抽屉的 `CSS规范` Tab 时，必须按页面级数据源审查，不能只看页面 HTML 或抽屉组件是否接入。

1. 先定位数据源：页面内联 `getDocCssContent(docId)`、模块级 `js/docs.js`、公共 `doc-panel.js`、公共 `doc-builder`，以及是否存在独立的 `DOCS_CSS_DATA` / CSS 规范映射。
2. 再定位成熟复用源：优先选同端、同抽屉组件、同数据结构的成熟页面；若没有同端成熟页，再按 Harness 的成熟基准与加权规则选择参考。复用源必须写到 `clone-source`，并标明具体 docId 或函数位置。
3. 审核每个目标 docId 是否具备 `颜色规范`、`字体规范`、`圆角规范`、`间距规范` 四类基础结构；颜色规范必须有色块或等价可视化表达，不能只列颜色值文本。
4. CSS 规范 Tab 的所有颜色、字号、圆角、间距取值必须来自当前页面 computed style 或页面源码真实值；禁止写记忆默认值、token 通用值、规划值或上一版旧值。页面实际用 `#2F6FFF` 时不得写成 `#1677FF`，即使后者是 token 默认主色。
5. 0-1 新页面的 CSS 规范同样必须先定值后写规范：以本页 `style` 块或页面内实际使用的 design token 取值为准；页面本身样式未确定时，先完成页面样式再写 CSS 规范，不得用占位默认值或凭空编造值填充规范。
6. 修复时只调整 CSS 规范 Tab 数据本身；不得顺手改真实页面 CSS、业务正文、入口导航、抽屉组件或需求文档正文，除非用户本轮明确要求。
7. 不得把某个业务页面的颜色值、字段名或状态名固化进 Harness；具体数值只能来自现有页面、成熟页、设计 token 或用户确认。
8. 完成后至少运行 `node --check` 检查被修改的 JS 数据文件、`git diff --check` 检查空白；若运行 `npm run check:ui` 触发登记脚本写入无关文件，必须识别并隔离该副作用。
9. 标准审核时对照 `DEVELOPMENT.md`、`standards/doc-spec.json`、`standards/ui-consistency-rules.json`：确认新增内容只是执行流程补强，不重复定义硬标准、不制造平行入口、不把单次业务案例泛化成全局规则。

## 任务分流

### 页面或原型执行

1. 读 `AGENTS.md`。
2. 按页面类型读 `DEVELOPMENT.md` 与 `standards/page-type-guide.md`。
3. 若是复刻改造，先声明 `clone-source` 与 `change-type`，再读 `standards/page-baseline-spec.json`。
4. 若涉及抽屉或需求文档，读 `standards/doc-spec.json`。
5. 修改后运行最窄相关检查，默认从只读检查 `npm run check:ui:readonly` 开始；只有明确需要补登记时才运行会写入文件的 `npm run check:ui` 或 `npm run register:missing:write`。

涉及复刻时，`clone-source` 必须包含具体路径、页面身份和说明数据源位置；若是截图，必须标为 `visual clone-source`，并区分可直接复刻项与待确认业务项。未打开源页面或未定位 docs 数据源时，不得声明已复用成熟页面。

### 用户提供截图要求按图复刻

1. 默认口径：用户提供截图时，通常要求复刻截图中的布局、信息层级、字段、按钮与可见业务文案；样式、组件密度、颜色、圆角、阴影、图标、抽屉和右侧控制区仍按当前端现有成熟风格适配，不做跨产品 100% 照抄。
2. 除非用户明确说“完全照抄”“样式也照截图”“按截图 1:1 复刻”等，否则截图不自动覆盖本仓库的 Web / App / 小程序视觉基线、设计 token、抽屉基线和静态原型边界。
3. 执行前必须先判断截图来源：仓库既有设计稿、线上页面、外部系统 / 竞品、领导草稿 / 标注图、业务沟通截图；无法确认来源时，在执行依据中标为“用户提供截图，来源待确认”。
4. 截图可以作为 `visual clone-source`，但仍需声明 `clone-source` 与 `change-type`；如果截图对应仓库或线上既有页面，还必须继续定位真实页面路径、入口和说明数据源，不能只按图片猜。
5. 执行前必须先判断截图用途：`能力结构参考`、`视觉布局参考`、`业务字段事实` 或 `混合参考`。能力结构参考只允许下放流程、步骤、信息层级和操作能力，不允许把截图中的后端能力说明、需求说明、开发说明或跨端来源说明写进真实页面。
6. 可直接复刻的内容：布局顺序、区块层级、字段名称、字段相对位置、按钮数量与可见文案、列表 / 卡片 / 表单的信息组织。
7. 不能仅凭截图写成事实的内容：接口字段、字段枚举、状态流转、权限规则、金额公式、异常处理、统计口径、数据来源、真实交互逻辑；这些只能依据需求文档、接口文档、现有页面或用户明确确认落地。
8. 截图中的视觉表现与平台成熟风格冲突时，默认保留截图的信息结构，视觉层适配当前端成熟页面；如果用户明确要求保留截图视觉冲突点，执行前标为 `breaking-change` 或待确认项。
9. 不得为了“像截图”自行新增动态联动、实时校验、mock 数据流程、额外提示、测试项或验收项；除非用户明确要求，否则仍按静态原型规则执行。
10. 抽屉或文档引用截图时，只能说明“依据用户提供截图复刻布局 / 字段 / 信息层级”；对未确认的业务含义必须写为 `待确认`、`推断` 或 `现有文档未确认`。
11. 需求抽屉引用截图时，推荐固定写法：`依据用户提供截图，页面布局、字段与可见文案按图呈现；视觉按当前端成熟风格适配。` 截图未确认的字段含义、接口、状态、金额、权限、异常处理，必须进入待确认项，不得进入字段规则或验收口径。
12. 执行前必须输出截图复刻矩阵，至少包含：截图用途判定、截图直接复刻项、按当前端成熟风格适配项、不可凭截图写成事实项、不得进入真实页面的截图文案、待确认项、可见字段/按钮/标签逐项清单。清单中每个可见字段都必须标注“保留 / 合并 / 改名 / 不展示及原因”，不得遗漏后只用“已按截图复刻”概括。
13. 若截图信息结构与仓库成熟页面风格都需要保留，默认优先级为：业务字段与可见文案不遗漏 > 信息层级不反转 > 当前端视觉基线不破坏 > 非关键装饰相似。只有用户明确要求 1:1 时，才允许把截图视觉优先级提升为 `breaking-change` 待确认。

### 业务原型轻量模式

当用户明确说“只保留业务原型 / 轻量原型 / 先别统一化 / 业务表达优先 / 不要平台化重做”时，进入业务原型轻量模式。

1. 仍遵守 `AGENTS.md`、T0 安全红线、执行依据和静态原型边界。
2. 不主动做平台级视觉大收口、抽屉重构、模板化改写或跨页面统一。
3. 只保留本轮业务表达所需的页面结构、字段、状态和最小交互。
4. 需求抽屉只写本轮业务必须说明的字段、规则、边界和待确认项。
5. 不新增测试项、验收项、平台治理说明、开发备注或额外统一规范。
6. 该模式不删除、不隐藏、不绕过仓库规则；只是降低本轮交付复杂度，避免局部业务原型被过度统一化。
7. 与截图复刻同时出现时，默认复刻截图的信息结构与字段，视觉仅做当前端基础适配，不按平台标杆做大范围重构。
8. 仍需保持当前端基础可读性、资源路径、抽屉可用性和页面边界，不得以轻量模式为由做低保真草稿或破坏现有端内风格。

### 需求抽屉或文档执行

1. 优先确认说明数据源：页面正文、右侧控制区、内联 `DocPanel`、模块 `js/docs.js`、公共 `doc-builder/doc-panel`、`需求文档.md`。
1.1. 新增或迁移单页需求抽屉时，默认使用页面级增量数据源 `js/docs/{docId}.js`，由目标页面在模块级 `js/docs.js` 之后加载并合并对应 docId。只有当同一 docId 确实被多个页面共享、或既有模块架构只能通过模块级数据源承载时，才允许写入模块级大 `js/docs.js`；执行前必须说明共享依据。
1.2. 禁止为了单页新增需求把 docId 直接追加到模块级大 `js/docs.js`。该做法会改变公共 docs 文件内容 hash，导致所有引用它的 HTML 在 `cache:bust:write` 后连带变更，制造无关 git diff。
1.3. 页面级 docs 文件的加载顺序必须可验证：公共 `doc-builder` 和模块级 `js/docs.js` 先加载，页面级 `js/docs/{docId}.js` 后加载，`doc-panel.js` 打开时能读取最终合并后的内容；若目标端使用 `window.DocsData` 或其他命名空间，页面级文件必须沿用对应命名空间，不得新建平行数据结构。
2. 普通迭代默认 `drawer-first`。
3. 大需求、跨多页、0-1 独立模块或用户明确要求时，才用 `md-required`。
4. 新增口径默认内联到具体字段、规则、边界条目中，不用顶部摘要代替正文定位。
5. 抽屉正文中的版本标记必须由渲染层转为扁平标签，不得只作为纯文本展示。

10. 既有功能迭代的需求抽屉应将已上线基线与本期变更分区展示：既有逻辑使用低强调分区，当前迭代使用橙色扁平标签或高亮分区；不得把新旧规则混写在同一条说明中。

11.2. 同一迭代内的日期增量写入所属迭代区块内部，例如 `0626 新增逻辑` 放在 `202606下` 区块内；后续 `202608` 等新迭代继续在上方新增独立区块，不得继续把新规则插进历史需求说明正文后靠标签堆叠。

12. 本项目所有原型的业务对话框默认不得使用浏览器视口级半透明遮罩阻断右侧需求抽屉滚动和点击；除非用户明确要求遮罩，否则 App 手机稿弹窗必须限定在手机模型内部，Web / 小程序 / 迭代索引 / iframe 承载页的居中对话框必须使用透明且非阻断的弹层，或只对页面局部容器生效。
13. 迭代页新增老功能控件时，若用户或现有口径明确“沿用既有逻辑”，原型只做静态控件展示或禁用态占位；需求抽屉写“沿用既有页面的控件、输入限制和异常反馈”，不得为了证明能力补写搜索、筛选、校验等真实交互细节。
14. 从已上线页面复用搜索、筛选、选择器等成熟控件时，抽屉只说明复用来源和本页差异；没有差异时不要重复展开老逻辑，避免引发开发测试按新需求追问。
15. Web 后台筛选控件需要复用既有样式时，优先参考迭代索引中运营侧成熟记录页（如 `迭代索引/202604下.html` 的运营记录页）的筛选区；新增页只说明复用筛选控件样式和输入限制，不额外补搜索实现细节。
16. 新增或引用某个具体端页面时，必须同步完成该端真实入口闭环：平台/模块 `index.html` 菜单项或模块卡片、页面承载区或跳转 `href`、`pageNames` / 面包屑 / URL 参数映射三者都要检查；只在文件夹新增页面、只登记到 `standards/ui-spec.json`、或只放入迭代索引，都不能视为该端页面已交付。
17. 新增源页面后，必须声明迭代引用策略：不挂迭代、挂当前迭代、进入待排期或冻结历史快照。无法从用户本轮要求、迭代索引或明确排期判断时，必须向用户确认，不得擅自挂入最新或历史迭代页。
18. 如果迭代索引引用的是某端已有页面作为本期源页面，该端菜单中也必须有对应本期标签入口；例如管理后台 202605 下新增 `设备可视化`，除 `迭代索引/202605下.html` 外，还必须同步 `admin-portal/store-admin/index.html` 的 202605 分组菜单、iframe 承载区和 `pageNames`。

20. 历史迭代索引不得直接 iframe 仍在持续演进的三端源页面；源页面始终代表最新设计稿，历史迭代必须引用 `迭代索引/snapshots/{迭代}/` 下的快照页。快照页必须声明 `snapshot-of`、`snapshot-iteration`、`snapshot-date`。快照必须冻结影响历史展示和需求口径的依赖闭包，包括页面 HTML、页面私有 JS/CSS、需求抽屉 `docs.js`、`doc-panel.js`、图片、下载模板和必要资源路径；不得继续读取三端源目录下可变 `js/docs.js` 或最新页面内 `DocPanel` 数据。修改 `迭代索引/*.html`、`迭代索引/snapshots/**`、被历史迭代引用的三端源页面，或运行 `cache:bust:write` 后，必须执行快照保护检查：历史页 iframe 是否全部指向 `snapshots/{迭代}/`、快照文件是否存在、快照元信息是否齐全、快照本地资源是否存在、菜单 `data-page` / iframe `page-*` / `pageNames` 是否一致、页脚数量是否与菜单一致。发现任一污染项时，必须先停止当前业务需求并报告，不得继续新增页面、调整目录或判断 `design over`。
21. 需求原型默认不写字段名与后端接口的映射对齐。字段命名对齐是开发侧职责，需求抽屉只描述页面展示的字段含义、枚举值和业务规则。只有在对接外部第三方接口、且字段名与页面展示名差异显著影响开发理解时，才在需求抽屉中补字段映射行。

23. 同一正式页面新增本期需求抽屉时，必须先检索该页面已有的 `DocPanel.toggle(...)`、`DocPanel.autoShow(...)` 和模块 `js/docs.js` 中对应历史 `docId`；除非用户明确要求下线或替换旧入口，否则不得把既有历史 `docId` 改成新 `docId`。新增需求只能采用并列按钮、补充入口、同一抽屉内追加分区或新增独立页面入口承接，并在修改后用检索结果确认历史 `docId` 仍可从页面打开。
24. 需求文档按钮默认打开不得依赖猜测。若按钮点击事件直接写 `DocPanel.toggle('docId')` 或 `toggleDocPanel('docId')`，可由公共扫描逻辑自动打开；若按钮通过 `openDoc()` 等包装函数打开抽屉，页面必须显式调用 `DocPanel.autoShow('docId')`，并在验证中确认首次进入页面抽屉已打开。
24.1. 所有 `迭代索引/*.html` 顶层索引页承载业务页面时，必须在父页层强制打开子页面需求抽屉；切换菜单后也必须再次触发当前 iframe 的需求抽屉打开。该规则只作用于迭代索引入口，不改变 Web 源页面独立访问时默认关闭、App/小程序源页面默认打开的三端基线。
24.2. Web 后台之外的移动端原型，包括 App、小程序、设备端、影像采集和后续 Pad/平板模型，需求抽屉打开时必须启用移动端画布避让布局：主画布、手机/平板模型和右侧模拟操作区整体进入抽屉左侧可用空间；模拟操作区不得使用浏览器视口最右侧 `fixed right` 定位；需求按钮、模拟区与手机/平板模型应放在同一页面容器内排布。若页面被 iframe 承载导致宽度不足，抽屉宽度必须按可用空间收敛，且验证中必须确认手机/平板模型、模拟操作区、需求抽屉三者矩形不相交；同时确认手机/平板模型没有被父级菜单、iframe 边界或浏览器边界裁切。该规则不适用于 Web 后台列表、详情、表单类页面。
25. 跨端同一需求的需求抽屉必须先定义统一章节骨架，再按端差异填充。若管理后台、作业端 App、用户端 App 等端使用不同章节名或不同颗粒度，必须在执行矩阵中说明差异原因；无原因的章节漂移视为未收口。
26. 需求抽屉只描述当前有效业务口径。旧方案、未交付方案或执行过程中的排错信息不得反复写入正文；如必须说明禁用项，只写成当前规则的正向限制，例如“状态筛选仅展示 A/B/C”，不要写成大段“不展示旧口径 X/Y/Z”。
27. 需求抽屉必须用最短可执行业务口径表达规则，不写推理过程和防误解长句。统计口径、权限口径、筛选口径等能用一句话表达时，不得补“避免重复计数”“开发测试会误解”等解释性理由；理由只在评审回复或开发文档中说明。
28. 所有筛选项、表单项、导入字段和开关类字段必须写默认值。下拉写默认选项，输入框写默认空值或默认带入值，复选框/开关写默认选中状态。若控件视觉是复选框但业务只能单选，必须明确“复选框样式、单选职能”，并写清不能多选。
29. 列表长文本字段必须写展示与溢出规则。已确认最大长度的字段写最大字符数；列表列宽不足时必须说明是否省略、是否鼠标 hover 气泡展示完整内容、是否支持复制。没有这些规则时不得交付给开发。
30. 唯一性、重复校验和权限范围必须写清业务作用域，作用域只能来自页面入口、现有页面、需求文档或用户确认。不得把“门店范围”“站点范围”“账号范围”“公司范围”互相替代；来源不明时写待确认。
31. 取消、删除、作废、解绑、停用等会使规则或数据失效的操作，需求抽屉必须写二次确认。二次确认文案只保留操作对象、核心后果和确认动作，不写长段背景说明。
32. 凡需求要求写包裹操作日志、业务操作日志或审计日志，抽屉必须逐项写清：记录时机、时间取值、操作内容文案组成、账号取值、展示位置、操作列是否有按钮。若操作列无按钮，必须明确“操作列无需按钮”。不得只写“新增一条日志”。
33. 若用户本轮已逐条裁决待确认项，必须按“用户纠偏口径收口”先移除待确认和旧错误口径，再写入当前有效规则；不得把用户裁决继续包装成待确认项。
34. 需求抽屉中描述输入框提示、搜索提示、按钮提示时必须使用中文业务表达；禁止把 `placeholder` 等技术属性名作为业务字段或规则文案。
35. 条目级标记解除与全局规则取消必须分开写。普通端通常只解除当前条目标记；具备管理员权限的端执行“取消规则”时才取消规则本身。不得把“解除当前条目标记”写成“删除/取消管理后台规则”，也不得反过来。
36. 筛选查询区只写控件类型、默认值、输入限制、数据来源和必要的清空/空结果规则；不得为每个筛选字段单独堆“按该字段查询”“非空时查询”这类无信息量列。若查询方式完全沿用既有逻辑，只写“沿用既有查询逻辑”或不写，不得伪造精确/模糊/接口确认口径。
37. 不得为了“看起来完整”虚构不存在的默认值、默认计费、默认金额、默认品牌或默认规则。当前业务只有“为空”时，只写“为空”；不得写“不套用默认值”“不套用计费规则”等暗示系统存在该默认规则的反向说明。
38. 列表字段分区只写展示规则，包括字段来源、为空展示、脱敏、截断、hover、复制和状态标签。必填/选填、失败归类、字段格式、导入校验、后续链路应归入表单/导入/功能区，不得混进列表字段说明。
39. 业务对话框默认在弹窗 header 右上角接入需求文档入口。只要页面存在对话框（新增/编辑/查看/批量/申请类弹窗），就必须在 `modal-header` 内、关闭按钮左侧放置"需求文档"按钮，调用 `toggleDocPanel('{dialogDocId}')` 或 `DocPanel.toggle('{dialogDocId}')`，让用户在弹窗内即可打开该弹窗的字段/规则说明，不必返回列表顶部找入口。
    - 按钮样式复用成熟页弹窗 header 的蓝底小按钮：`background:#f0f9ff;color:#0369a1;border:1px solid #bae6fd;`，高度 28px，字号 12px，与关闭按钮用 `gap:8px` 并排。
    - `modal-header` 结构统一为 `<h3>标题</h3>` + `<div style="display:flex;align-items:center;gap:8px;">` 包裹"需求文档"按钮和关闭按钮，避免按钮溢出或错位。
    - docId 命名：若弹窗业务独立于列表（如申请类、配置类弹窗），用独立 docId（如 `demo-apply`、`demo-config`）；若弹窗只是列表行的详情/编辑且字段与列表同源，可复用列表 docId。
    - 拆分例外：只有当弹窗业务与列表页业务口径明显不一致，或弹窗逻辑特别复杂（多步表单、跨模块联动、独立状态机）需要单独成章时，才为弹窗拆分独立 docId 并在 `docs.js` 单独定义；否则复用列表 docId 即可，不强制拆分。
    - 同一页面多个弹窗各自有独立业务时，每个弹窗 header 各接自己的 docId；不得多个弹窗共用一个 docId 导致说明错位。
    - 已落地参考：示例项目管理后台成熟页（如 `admin-portal/store-admin/pages/资产管理.html` 的配置弹窗）。
    - 该规则不适用于纯系统提示框（confirm/alert）、loading 遮罩、图片预览等无业务字段的非业务弹窗。
40. 纯 UI 调整类任务（无业务逻辑、字段、状态或接口变更）的需求抽屉只写「页面元素清单」与「操作按钮表」（按钮名称 / 形态 / 反馈文案）；不写交互流程、页面边界、状态流转、接口映射或业务规则说明。业务规则类说明只在存在真实业务变更时写入。
41. 需求抽屉正文禁止写入页面承载与导航的实现细节，包括但不限于：`iframe` 承载、`window.parent`、`goBackPage`、回退历史、独立打开时的路由策略、事件监听、DOM 操作、脚本调用方式。这些属于设计稿的实现说明，不属于业务需求；需求抽屉只写业务口径，例如返回行为写「返回上一页」，不写「iframe 承载时调用 window.parent.goBackPage，独立打开时回退历史」。命中既有成熟页面（如设备详情页的 `goPage`/`goBack`）时同理，抽屉不复述其实现。
42. 单张规则卡内容超过约 150 字或含多个子维度时，卡内必须按功能/按钮/交互/边界再分组（小标题、分段或留白），宁长勿挤；规则卡网格默认一行一卡，短枚举最多两卡，禁止三卡并排。细则见 `standards/doc-spec.json` 的 ruleCardColumnRule 与 cardInternalGroupingRule。
43. 设计稿呈现的新页面在线上可能对应既有老功能（线上已有完整逻辑，本期只是新增某个按钮、交互或局部逻辑）；需求抽屉必须判断并只写增量部分与承接关系，禁止把线上老逻辑全量复述一遍。判断依据：用户对话原话、仓库既有页面与需求文档；无法确认是否老功能时列为待确认，不得默认全量重写。
44. 页面内给用户看的提示文案（toast、警告条、空态等）只写用户视角的行动指令，禁止出现系统内部判断与实现机制类表述（如「系统无法区分」「后端判定」「接口校验」）；文案定稿后需求抽屉同步为同款文案。
45. 用户要求删除页面元素时必须整元素移除：HTML 结构、对应 CSS、对应 JS（含取值赋值与事件）三处联动删除，不得只删内容留空壳；交付前对已删标识符 grep 断言零残留。
46. 跨页面复刻组件时，CSS 规则块与卡片 HTML 必须用编辑工具从源文件逐字复制，禁止凭阅读记忆手抄重写；源页面存在 JS 运行时归一化（如首页 `normalizeCards()`）时，必须先以 Puppeteer dump 运行时 DOM 与 computedStyle 作为复刻基准，静态 HTML 不算真实形态。

### 业务逻辑审查 Harness

→ 细则已外置 `harness/rules/业务逻辑审查细则.md`（触发词：审阅需求/批判审查/看看有没有漏洞/业务流有没有问题/需求抽屉收口/感觉差不多了）

### design over 判断

1. 必读 `standards/design-over-spec.md`。
2. 结论只允许：`可打标`、`不可打标`、`待确认`。

### 故障排查

1. 使用 `engineering-diagnose`。
2. 先复现或定位失败命令、页面异常、控制台错误或脚本链路。
3. 只做最小修复，不顺手重构。
4. 区分本次新增问题与仓库存量问题。

### 页面可见改动无效诊断

当用户反馈“页面没变化 / 还是一样 / 没效果 / 诓我 / 看不到改动”时，不得继续沿原理解补改，必须先按以下顺序定位：

1. 实际加载文件：确认当前入口、iframe、URL 参数、`pageNames`、菜单 `data-page` 或跳转路径加载的是本轮修改的源文件，不得只看工作区文件路径。
2. 缓存与版本：检查 HTML/CSS/JS 引用版本号、浏览器缓存、手动上传缓存策略和线上/本地访问地址；未上传时只能判断本地，不得断言线上已生效。
3. 遮挡与默认面板：检查需求文档抽屉、CSS 规范抽屉、遮罩、右侧面板、业务弹窗层级是否盖住目标页面；必要时先关闭抽屉或面板再截图验证。
4. 触发链路：实际点击或调用目标按钮/入口，读取目标 DOM class、display、innerText、computed style 或 URL 变化，确认交互是否生效。
5. 可见证据：输出触发入口、目标 DOM 状态、关键可见文案和截图路径；未完成这些证据前，不得说“页面已变 / 已修复 / 已按截图下放”。
6. 连续失败：同一可见问题两轮仍无法证明生效时，停止继续猜测，输出诊断报告和下一步需要的用户确认或环境动作。

### CSS/布局不生效诊断

当页面元素布局、样式与预期不符时，必须按以下顺序排查，不得先在 CSS 层反复猜测：

1. 查浏览器解析后的 DOM 结构：输出目标元素及最近三层父级结构；重点检查 `<p>` 包裹块级元素、标签未闭合、列表或表格层级违法等问题。
2. 查 computed style：确认目标元素的 `display`、`grid-template-columns`、`flex-direction`、`position`、`z-index` 等关键属性是否按预期生效。
3. 查覆盖源：定位属性来自 inline style、class、组件样式、公共样式还是浏览器默认样式；同优先级冲突时检查书写顺序。
4. 再改样式：只有 DOM 结构和 computed style 排查完成后，才允许修改 CSS；优先最小修正结构或局部选择器，不直接堆全局覆盖。
5. 修后复核：再次检查 DOM 和 computed style，并说明视觉复核结果；相同思路连续无效不得超过两轮。
6. 无法打开浏览器时，第 1、2 步用源码结构审查和静态 CSS 来源审查替代，并在最终回复说明未完成浏览器复核。
