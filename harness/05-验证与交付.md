# 验证与交付

本文件承载验证命令、可见证据、手动上传、命令验证边界和 Git 收尾推送规则。

## 验证命令

| 场景 | 命令 |
| --- | --- |
| 页面注册只读检查、UI lint、UI 审计 | `npm run check:ui:readonly` |
| 文档审计 | `npm run audit:docs` |
| 全量检查 | `npm run check:all` |
| 补登记并写入 | `npm run register:missing:write` 或 `npm run check:ui` |
| UI lint | `npm run lint:ui` |
| UI 审计 | `npm run audit:ui` |
| 历史快照审计 | `npm run audit:snapshots` |
| 全量历史快照债务审计 | `npm run audit:snapshots:all` |
| 新页面脚手架 | `npm run scaffold:page -- --type <type> --out "<path>" --title "<title>" --register` |
| 手动上传前刷新缓存版本号 | `npm run cache:bust:write` |

## 窄验证默认口径

验证范围按改动面收敛，不按“能跑的都跑一遍”执行。

默认只跑与改动文件直接相关的最窄命令：

| 改动类型 | 默认验证 | 默认不跑 |
| --- | --- | --- |
| 页面 / 抽屉 / 样式 | `npm run lint:ui` + 浏览器复核目标页面 | `check:all`、`audit:ui`、`audit:docs`、`audit:snapshots`、`audit:export-stale` |
| 规则 / 文档 / 治理 | `git diff --check` | 同上 |
| 新增页面 | 追加 `npm run register:missing:write`（登记闭环） | 其余全量命令 |

默认不跑的命令只在以下情形执行一次，并在最终回复写明原因：

- 用户明确要求复核、上线前全量体检或专项治理。
- 本轮交付确实依赖该结果，例如页面登记闭环、迭代分组新增或调整下载入口。
- 命令为只读输出，不写文件。

凡会重写 `平台优化-*.md` 报告文件、`需求导出/**` 产物或 `standards/*` 登记的命令，都按本节口径收敛：不得为了展示严谨而在每轮重复运行，避免把存量问题和大体积产物混入本轮 diff。

需求包导出与过期审计的触发条件见 `harness/rules/需求分组导出能力.md#执行基线`；未刷新时必须在最终回复写明“需求包未刷新”，不得静默。

## 本地服务保护

本地预览服务可能是用户自己启动的常驻进程，AI 不得与之抢占，也不得结束它。

- 禁止使用 `pkill` / `killall` 或任何按进程名批量结束的方式清理服务；不得结束非本轮启动的进程。
- 预览前先探测：`curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:18765/`。已有服务直接复用，不重启、不换端口、不杀进程。
- 确需自行启动时，使用独立端口并记录 PID；收尾只结束该 PID，不按进程名结束。
- 已探明有可用服务时不得再启动第二个；不得以“清理环境”为由停掉服务。
- 误停用户服务时，必须立即说明原因和重启方式，并在最终回复单列为事故，不得静默。

## 手动上传缓存规则

当前线上通过内网固定地址手动上传访问（具体地址由部署方自持，不入库），服务器侧不协助配置缓存头。为避免同事上传文件夹后仍看到旧页面，手动上传前必须运行缓存版本号脚本：

```bash
npm run cache:bust:write
```

脚本只给本地 `.css` / `.js` 引用写入资源文件内容 hash，例如 `?v=<hash前8位>`；资源内容不变时 hash 不变，引用它的 HTML 不应产生新 diff。`.html` 链接只清理旧 `v=`，不得再写入新版本号，避免入口页、迭代索引和历史页之间出现链式版本号污染。

运行后必须立即复核：

```bash
node scripts/cache-bust-html.js
git diff --name-only -G '\.html\?v='
git diff --check
npm run audit:version-tags
```

验收标准：

- `node scripts/cache-bust-html.js` 输出 `Would update 0 HTML file(s) with content hash for CSS/JS and clean HTML links.`
- `git diff --name-only -G '\.html\?v='` 无输出。
- `npm run audit:version-tags` 无问题。
- 若 `audit:snapshots` 仍报 known debt 或既有 new issue，必须与本轮 cache-bust 回归分开说明，不得把存量快照债当作本轮 hash 失败。

默认规则：

- 只处理本仓库本地相对路径，不处理 `http://`、`https://`、`mailto:`、锚点和模板变量。
- 每次上传前重新运行；只有内容变化的 CSS/JS 资源才应得到新的 hash。
- 运行后必须把被脚本更新的 HTML 文件一并上传；只上传 CSS/JS 不上传引用它们的 HTML，缓存版本号不会生效。
- 新增或修改单页需求抽屉时，优先把新增 docId 放到页面级 `js/docs/{docId}.js`，并让目标页面单独引用该文件；不要为了单页说明改模块级大 `js/docs.js`，否则会让所有引用大 docs 的 HTML 连带更新。
- 该脚本不能替代服务器缓存头；若 HTML 本身被强缓存，需要从入口链接带版本号访问或手动刷新入口页。

## 命令验证不是功能验证

`lint:ui` 只验证页面登记、模板边界、`variables.css`、需求文档入口等规则；它不验证 CSS 布局是否真实渲染正确、生成 HTML 是否语义合法、按钮/弹窗/抽屉交互是否可用、需求文档内容是否业务正确。

CSS、布局、抽屉正文样式、交互可用性相关修改完成后，必须在命令结果之外说明功能或视觉复核结果：

- 已用浏览器或等效工具复核，确认目标效果正确。
- 或：当前未完成浏览器复核，并说明原因和剩余风险。

不得只用“命令通过”证明 CSS/布局/交互类修改已经正确。

规则违反的后果分三类：

| 后果类型 | 触发方式 | 处理口径 |
| --- | --- | --- |
| 硬失败 | `npm run lint:ui`、`npm run check:ui:readonly` 或 `npm run check:ui` 直接退出失败 | 必须修复后才能声称页面通过基础检查 |
| 审计报告问题 | `npm run audit:ui`、`npm run audit:docs` 输出问题清单但命令可能退出成功 | 最终回复必须说明是本次新增还是仓库存量 |
| 人工边界问题 | 静态原型越界、复刻越界、无依据编写规则、讨论态改文件 | 即使命令不报错，也必须回退或标为待确认 |

人工边界问题优先级高于命令通过。若发现讨论态改文件、静态原型越界、无依据写业务事实、页面混入开发说明、复刻未声明来源，必须先修正或回退该部分，不能用“命令通过”覆盖。

治理文档类变更至少运行 `git diff --check`，确认没有尾随空格和明显补丁问题。若未运行 UI 或 docs 命令，最终回复必须说明原因。

## 验证截图产物处置

截图是 AI 的自查手段，不是交付物：截图验证完成后必须立即删除验证截图文件（含 tmp/ 等临时目录中的验证用途 PNG），不得留在工作区、不得列入交付清单或上传清单。用户通过打开真实页面查看效果。

例外：只有用户明确要求交付截图（评审材料、投标素材、迭代对比留档等）时才保留，并按用户指定路径归档；未指定路径时询问，不得默认散落临时目录。

## 规则引用自报落盘

文件执行态任务收尾时，必须把本轮开工声明中「本轮已读取的规则文件」清单追加写入 `.harness-runtime/rule-usage/YYYY-Www.jsonl`（ISO 周命名，每行一条 JSON：`{"date":"YYYY-MM-DD","task":"任务摘要","rules":["harness/10-页面与抽屉执行.md#视觉改动前强制三查","standards/ui-consistency-rules.json#typography"]}`）。`rules` 数组条目必须带章节锚点（`文件#小节名`），不得只写文件路径——文件级统计无法支撑条目级冷宫移出。该目录已被 gitignore，仅用于每周五规则频率审计与冷宫候选产出；漏报只会使规则偏低频，方向保守可接受，不要求补报。

## 需求收尾与推送闸门

每个需求或治理任务完成后，必须执行 `git status --short --branch`，并在最终回复前区分本轮改动、既有非本轮改动、未跟踪文件和禁止触碰范围。

若用户已给出“该推送就推送”的长期口径，且本轮改动已通过最窄相关验证，AI 应优先提交并推送本轮范围内的文件。提交前必须确认暂存区只包含本轮改动；若目标文件已有非本轮 hunks，必须只暂存本轮 hunks，无法安全拆分时不得强行提交。

禁止把历史 dirty、其他需求页面、未核验快照、执行者遗留文件夹或无关生成物顺手提交。提交信息必须能对应本轮需求或治理目标，不能使用 `update`、`fix` 等无法追溯的泛化信息。

“推一下 / 上传一下 / 发布一下 / 提交一下”默认只授权本轮改动，不等于整树授权。只有用户明确说“整树 / 全量 / 全部文件 / git add -A / 全量提交 / 全量推送 / 把所有 dirty 都处理掉”时，才允许进入整树专项流程。

普通需求收尾禁止使用 `git add -A`、整树提交、批量回滚或批量格式化来处理脏工作区；提交或推送前必须能证明暂存区只包含本轮改动。若目标文件已有非本轮 hunks 且无法安全按 hunk 暂存，必须停止提交/推送，并在最终回复列出阻塞文件和原因。

最终回复必须说明：是否已提交、commit hash、是否已推送、当前分支与远端同步状态；未提交或未推送时，必须说明阻塞原因。
