# 协作角色路由与专项审阅

本文件负责本项目三个协作角色的自动路由、跨会话交接边界和专项审阅补充。角色完整正文只维护在 `harness/roles/`，本文件不再复制指导者、执行者、agent1 或 agent2 的重复 Prompt。

本文件不替代 `AGENTS.md`、业务外脑、其他 Harness 分卷、`DEVELOPMENT.md` 或 `standards/*`。

## 共同约束

- 命中角色后先读 `AGENTS.md`、`memory/MEMORY.md`、本文件和对应角色正文，再按任务路由读取其他规则；业务判断另读业务外脑。
- 项目规则优先，记忆只作事实指针；无法读取材料时必须说明，不得假装已读。
- 角色切换和任务包存在都不构成文件授权，授权只认 `standards/授权词表.md`。
- 子 agent 不继承父 agent 的文件授权：收到发包、接力摘要或口头指令后，必须自行读取当前项目规则与 `standards/授权词表.md`，逐字核验用户最新消息中的 L3 授权是否覆盖自身目标文件、范围和交互；父 agent 已声明通过闸门、上一轮已有授权、角色切换以及“改吧”等模糊表达均不得作为写入依据。核验不到 L3 或对象不明确时，子 agent 只能停在只读审查并回报阻塞。
- 修改前执行 `harness/01-强制闸门.md`，完成后按 `harness/05-验证与交付.md` 收口。

## 职责与审查维度隔离

`business_logic`、`ux_interaction`、`ui_visual`、`delivery_acceptance`、`drawer_css` 是按任务命中的审查维度，不是永久角色、固定编制或自动创建的子 agent。任务只区分产品主管、方案作者、执行者和对抗审查者四类职责；canonical 文件只是工作入口。

方案作者不得审查自己的方案，执行者不得签收自己的交付；对抗审查者负责决定命中维度、记录不适用原因并核验证据。每个维度需记录 `review_id`、`review_dimension`、`reviewer_id` 和 `independence: isolated | single_context`。单上下文仅标记挑战审查，不得声称独立对抗通过。

## 自动路由

职责入口判断以用户最新消息为准；审查维度由对抗审查者按改动命中判定：

| 触发表达 | 路由结果 |
| --- | --- |
| 需求聚焦、需求姿态、需求访谈、梳理需求、需求不清楚、先问清楚、需求再聊聊 | 读取 `harness/roles/需求聚焦者.md` |
| 需求审阅、指导姿态、生成任务包、产出任务包、拆任务包、发包 | 读取 `harness/roles/指导审阅者.md` 的指导发包模式 |
| 审阅任务包、审阅执行结果、审阅姿态、对抗式审查、帮我审一下方案 / 交付 | 读取 `harness/roles/指导审阅者.md` 的对抗审阅模式 |
| 执行任务包、按任务包执行、继续执行任务包、执行者姿态、工程执行、按刚才的包继续干 | 读取 `harness/roles/通用执行者.md` |
| 审一下抽屉 / 抽屉写对没 / 检查需求说明 / 检查 CSS 规范 / 抽屉能进评审会吗、抽屉审查 | 读取 `harness/roles/抽屉审查者.md` |

路由规则：

1. 用户明确指定角色时，明确指定优先于关键词自动判断。
2. 每条最新消息都重新判断角色，上一轮角色不构成继续沿用依据。
3. “生成 / 产出 / 拆解任务包”属于方案作者使用指导发包入口；“执行 / 按 / 继续执行任务包”属于执行者使用通用执行入口。
4. 单独出现“审阅 / 审查”时结合对象判断：需求抽屉与 CSS 规范进入 `drawer_css` 维度审查入口；需求、任务包和执行交付进入对抗审查入口；代码、产品审美、UI/UX 等对象读取 `doc/UI-设计工作流.md` 按场景执行专项审阅（视觉审查 neat-freak + 产品技术审查 impeccable critique/audit）。
5. 审查对象不明确时，只确认对象，不修改文件。
6. 用户消息未命中任何角色信号时，默认按通用执行者姿态执行（受授权词表与 harness/01 闸门约束，非角色授权）。
7. 以“山”开头只证明命中握手词；命中角色后必须真实读取对应文件并提供适用场景所需的规则、范围和验证证据。

## 跨会话使用

- 分开会话使用时，每个会话可以固定加载一个职责入口文件；最新用户消息明确切换职责或审查对象时重新读取对应正文。
- 同一会话使用时，需求聚焦者完成需求基线后，可切换指导审阅者生成任务包；任务包交给另一个会话的通用执行者执行。
- 跨 agent 发包时，父 agent 必须在任务包中附上“授权待核验”字段，但该字段只是待核验线索，不是授权本身；子 agent 开工前仍须独立完成 `harness/01-强制闸门.md` 的子 agent 独立授权核验，并在回执中分别列出用户最新授权原文、父 agent 指令、实际授权覆盖范围、未覆盖目标及停手原因。
- 指导审阅者收到执行者回复后，必须把 `执行者声称` 与 `本地已验证` 分开；执行者最终回复不能直接视为完成证据。
- 输入包含上一位 AI 结论、执行者回复、接力摘要或历史审阅时，先按 `harness/02-纠偏与接力.md` 做五分层。

## 任务包和交付证据

- 页面、抽屉、字段、状态、文案或跨页任务的任务包，先按 `harness/03-任务契约.md` 形成页面调整契约。
- 规则治理任务可复用 `templates/规则任务包模板.md`。
- 执行者最终回复应对照 `templates/执行者最终答复模板.md`，让指导审阅者能够把声称逐项核验为本地事实。
- 指导审阅者不得因为任务包由自己产出就降低审查强度；发现任务包自身错误时，应停止继续让执行者照错包修复。
